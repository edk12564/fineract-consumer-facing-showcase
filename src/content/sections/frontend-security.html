Security

The Angular client holds no secrets and enforces no policy. Both jobs belong to the BFF (backend-for-frontend, the Spring Boot service in consumer/). Tokens live in cookies the page’s JavaScript cannot read, authorization decisions happen server side, and every client-side check described here is a convenience, not a defense. This chapter describes how the client cooperates with that model. It covers the session and token lifecycle as the client experiences it, the identifier the client presents for its device, the step-up challenges it drives for sensitive actions, and the way it keeps personal data out of browser storage and audit events. Each section names the BFF security section that holds the server half of the story.

Session Model

This section describes how the Angular client logs in, stays logged in, and is logged out under the BFF’s token model. The client never sees a token value. Both session tokens travel in httpOnly cookies (browser cookies that page JavaScript cannot read), set and read only by the BFF. The server half (token contents, lifetimes, rotation, and validation) is described in docs/consumer/security/tokens.adoc.

The client code involved is frontend/src/app/core/auth/auth.service.ts, core/interceptors/error.interceptor.ts, core/guards/auth.guard.ts, app.config.ts, and features/auth/login.component.ts.

What the client actually holds

AuthService keeps exactly one piece of session state: a signal (an Angular reactive value that templates re-render from) named sessionExpiresAt, holding the access-token expiry timestamp the BFF returns in the 2FA and refresh response bodies. A computed isAuthenticated is simply sessionExpiresAt() !== null.

Nothing else exists on the client: no token string, no user object, no entry in localStorage (a persistent key-value store in the browser). The cookies ride along automatically on every request because the browser attaches them; the client cannot inspect them even if it wanted to. A consequence worth knowing: isAuthenticated is a belief, not a fact. The authoritative check happens on the BFF for every request.

Login is two steps

LoginComponent drives the flow with a step signal (credentials or otp):

  1. The credentials form posts email and password via AuthService.login (POST /api/v1/authentication/login). A success does not create a session; it returns a challenge (a challengeToken string plus sentTo, the masked email an OTP was mailed to). The component keeps the challenge token in a private field and switches to the OTP step, rendered by the shared OtpComponent.

  2. The submitted code goes to AuthService.verifyTwoFactor (POST /api/v1/authentication/2fa) together with the challenge token. On success the BFF sets both session cookies and the service adopts the returned expiresAt into the signal. The component then navigates to /summary, or to a returnUrl query parameter. The returnUrl is honored only if it starts with /api/v1/oauth2/ (allowedReturnUrl), which is the open banking consent hand-off; any other value is ignored to prevent open redirects.

Silent restore at boot

Because the session lives in cookies, a page reload does not lose it, but the in-memory signal starts empty. app.config.ts registers a provideAppInitializer (code Angular runs before the first screen renders) that calls auth.refresh() once and swallows any failure with .catch(() ⇒ undefined). If the refresh cookie is still valid, the BFF rotates it, sets fresh cookies, and the signal is populated, so the user stays logged in across reloads. If not, the app simply boots unauthenticated and the route guard sends the user to /login.

Refresh, and why it is deduplicated

AuthService.refresh() calls POST /api/v1/authentication/refresh; the browser supplies the refresh cookie. The service keeps a single in-flight observable guarded by shareReplay(1), an RxJS operator that lets many subscribers share one HTTP call and its result. If several requests fail with 401 at the same moment, they all wait on the same refresh instead of racing the BFF with parallel rotations. The BFF has a 30-second grace window for honest races (see docs/consumer/security/tokens.adoc), but the client avoids creating them in the first place. finalize clears the slot when the call settles so the next refresh starts fresh.

The 401 path in the error interceptor

errorInterceptor wraps every HTTP call. Its handling, in order:

Failure Client behavior

Any error on the audit endpoint or on the refresh endpoint itself

Passed through untouched, so audit retries and refresh failures are handled by their callers, not recursively

403 with code error.msg.consumer.auth.device.fingerprint.forbidden

Device mismatch: clear the session signal and redirect to /login (see Device Fingerprint)

401 with no BFF error code

Treated as an expired access token: call auth.refresh(), then retry the original request once. If the retry fails 401 or 403, clear the session and redirect to /login; a 429 on retry shows the rate-limited toast

401 carrying a BFF error code

Not a session problem (for example an invalid step-up token); shown as a translated toast like any other error

The distinction in the last two rows matters: the BFF’s business denials arrive as 401 plus a machine-readable code, while a dead access token arrives as a bare 401. Only the latter should trigger a refresh.

Logout

AuthService.logout() calls POST /api/v1/authentication/logout, then clears the local signal. On that call the BFF denylists the access token, revokes the refresh token, and expires both cookies. The layout shell also records a LOGOUT audit event before calling it.

What the route guard checks

authGuard is one line of policy: it returns true when isAuthenticated() is set, and a redirect to /login otherwise. It reads only the in-memory signal; it makes no network call and proves nothing. Its job is user experience (do not render account screens that would immediately 401), not security. A user who tampers with client state past the guard still holds no valid cookie, and every BFF endpoint rejects them.

Device Fingerprint

Despite the name, the device fingerprint is not a fingerprint of anything. It is a random UUID (universally unique identifier, a 36-character random string) that the client mints once and presents on every request. The BFF binds it into refresh tokens and JWT claims so that a session stolen from one browser cannot be replayed from another. The server half (validation, the three binding points, and the per-request filter) is described in docs/consumer/security/tokens.adoc.

How the identifier is minted and stored

frontend/src/app/core/auth/device-fingerprint.ts exposes one function, deviceFingerprint():

  1. If a module-level variable already holds a value, return it (so the ID is read from storage at most once per page load).

  2. Otherwise read localStorage key bff.device-id. If absent, generate crypto.randomUUID() and store it.

  3. If localStorage throws (some private-browsing modes and embedded webviews block it), fall back to a fresh in-memory UUID that lives only until the tab closes.

The value is deliberately not derived from browser characteristics (screen size, fonts, canvas rendering and similar). A characteristics fingerprint would be a tracking mechanism and would still be forgeable; a random UUID is honest about what it is: a stable label for one browser profile.

How it reaches the BFF

Two paths carry the same value:

  • authInterceptor (core/interceptors/auth.interceptor.ts) clones each request whose URL starts with /api and sets the X-Device-Fingerprint header. An interceptor is a hook that runs on every outgoing HTTP request. The BFF’s DeviceFingerprintFilter requires this header on every authenticated request and compares it to the claim inside the access-token cookie.

  • The generated API client (@bff/client) declares the fingerprint as a required, typed first parameter on the sensitive methods: login, 2FA, refresh, and every step-up initiate/confirm. Feature code passes deviceFingerprint() explicitly there (see AuthService, TransfersStore, BeneficiariesStore, SettingsStore). The interceptor would have set the header anyway; the typed parameter exists so the contract is visible in the method signature and cannot be forgotten if the interceptor changes.

The audit batcher (core/audit/audit.service.ts) uses fetch directly rather than Angular’s HTTP client, so it bypasses the interceptor and sets the header itself.

What the binding buys

The BFF stamps the fingerprint into each refresh-token row and into the device_fingerprint claim of access, challenge, and step-up tokens. Because the cookies are httpOnly, an attacker who steals them (for example by copying them off a device backup or through a proxy) must replay them from a browser that also presents the matching header. Without the localStorage value, refresh with the current token fails with a device mismatch. The BFF revokes the whole session family only when an already-rotated token is replayed; on such a replay, a device mismatch triggers the revocation even inside the rotation grace window.

Client handling of a mismatch

If the BFF rejects a request with HTTP 403 and code error.msg.consumer.auth.device.fingerprint.forbidden, errorInterceptor treats the session as unusable on this device: it records an API_FAILURE audit event, clears the session signal, and redirects to /login. There is no retry: a mismatch cannot be fixed by refreshing, only by logging in again from this device.

What this does and does not defend against

Question Answer

Stops a stolen cookie replayed from another device?

Yes. The thief’s browser lacks the matching bff.device-id, so both ordinary requests and refresh attempts fail.

Stops an attacker who controls the victim’s browser?

No. Script running in the victim’s page (or anyone who can read its localStorage) sees the UUID; it is an identifier, not a secret.

Identifies a physical device?

No. It labels one browser profile. Clearing site data, switching browsers, or private-browsing mode mints a new identity, after which the user must log in again. By design, this costs a login, never data.

Enables cross-site tracking?

No. It is only ever sent to the BFF, and only on /api requests.

Step-Up Challenges

Sensitive actions require the user to re-prove control of their second factor immediately before the action executes, even with a valid session. The client’s job is small. It calls the initiate endpoint, shows the OTP entry screen, and echoes the challenge back at confirm time. Everything that makes the mechanism safe (the token’s binding to user, device, and exact action parameters, and the OTP hashing and attempt limits) happens on the BFF and is described in docs/consumer/security/step-up.adoc.

The client-side shape of every flow

Each screen follows the same three states, tracked in a step signal:

  1. Form. The user fills in the action (amount, payee, new password). Submitting calls the feature’s initiate endpoint through its store. The response is a challenge object: an opaque stepUpToken (opaque meaning the client never parses or inspects it; it is carried, not read), an expiresAt, and sentTo, the masked email the OTP went to.

  2. OTP. The store puts the challenge in a signal and the component switches to the shared OtpComponent (shared/otp/otp.component.ts), which shows the masked destination and collects a six-character code. Cancelling returns to the form; the abandoned challenge simply expires server side.

  3. Confirm. The component sends the confirm request containing the stepUpToken from the store signal, the entered OTP, and the full action parameters again. The BFF recomputes a hash of those parameters and rejects the confirm if anything changed since initiate. On success the store clears the challenge signal (challenge.set(null)) and the screen shows its done state.

The challenge lives only in that store signal, in memory: it is never written to localStorage or a cookie. Because the stores are root-scoped services, the signal survives in-app navigation; it is cleared on a successful confirm and lost on a full page reload. The token is short-lived (5 minutes) and useless as a session credential: the BFF’s access-token decoder rejects it outright because it carries a purpose claim.

Every initiate and confirm also passes the device fingerprint as a typed parameter (see Device Fingerprint); the BFF requires the confirm to come from the same device as the initiate.

There is no client-side registry of "actions that need step-up". A screen participates because its BFF endpoints demand it; the client cannot opt an action out.

Idempotency on money movement

The two transfer-backed confirms (transfer, loan repayment) additionally send an Idempotency-Key header: a client-chosen UUID that lets the BFF recognize a retried confirm and execute the transfer only once. The component mints the key lazily with crypto.randomUUID() and reuses it if the same confirm is retried after a network failure. It resets the key whenever the form values change (a changed form is a new action, not a retry) and clears it on success. Beneficiary and password-change confirms carry no idempotency key; they are naturally safe to retry.

Denials

A rejected confirm (wrong OTP, expired challenge, or tampered parameters) comes back as HTTP 401 with a feature-specific error code. Because the response carries a code, errorInterceptor does not mistake it for an expired session: no refresh is attempted, the session stays intact, and the user sees a translated toast. The component stays on the OTP step so the user can retry the code. Once the OTP’s attempt limit or either expiry is hit, the confirm keeps failing; the user then backs out to the form and initiates again, which mints a fresh challenge.

The login screen (features/auth/login.component.ts) reuses OtpComponent for its 2FA step but is not step-up: it elevates nothing, it creates the session in the first place, and its challenge token is held in a private component field rather than a store. See Session Model.

PII and Secrets on the Client

The client’s data-hygiene rule is simple: nothing secret and nothing personally identifying (PII: data that identifies a person, such as an email address or a government ID number) may persist in the browser or leave it through a side channel. This section covers what browser storage actually contains, how sensitive inputs are rendered, how the audit pipeline scrubs events before they leave the page, and how errors are displayed. The server half (encryption at rest, masked responses, and the BFF’s own PII screen) is described in docs/consumer/security/secrets.adoc and, for the audit gate, docs/consumer/features/audit.adoc.

What lives in browser storage

Grepping the application source for localStorage yields exactly two keys, and sessionStorage is not used at all:

bff.device-id

core/auth/device-fingerprint.ts

The random device UUID, an identifier rather than a secret (see Device Fingerprint)

app.lang

The chosen language code (for example en)

No token, credential, account number, or user attribute is ever written to storage. The access and refresh tokens are httpOnly cookies (cookies page JavaScript cannot read) managed entirely by the BFF; the session signal holds only an expiry timestamp; step-up challenges live in in-memory signals that vanish on reload (see Session Model and Step-Up Challenges).

Sensitive inputs

Fields whose value is a secret are rendered as type="password" so the value is masked on screen, kept out of shoulder-surfing range, and excluded from ordinary browser autofill history. These fields are the login and registration passwords, both password-change fields, the password-reset field, and, notably, the registration documentKey, which is the raw SSN or Aadhaar number (features/registration/registration.component.ts, with autocomplete="off"). After submission the BFF returns only maskedLastFour; the full number never comes back to the client. The OTP field (shared/otp/otp.component.ts) is visible while typed, since codes are short-lived and single-use, but it uses autocomplete="one-time-code" and is never stored or logged.

Audit events are scrubbed before they leave the browser

The client audit pipeline (core/audit/audit.service.ts) batches navigation, sensitive-action, and error events to POST /api/v1/audit/events. Every details map passes through buildDetails in core/audit/pii-scrub.ts before it is buffered:

  • Blocked keys. Entries whose key is password, otp, ssn, or token (case-insensitive) are dropped entirely, whatever their value.

  • Pattern redaction. scrubPii replaces anything shaped like an email address, a 9-digit run (SSN-like), a 12-digit run (Aadhaar-like), or a 13-to-19-digit run (card-number-like) with [REDACTED].

  • Length cap. Each value is truncated to 300 characters, bounding how much of any unexpected payload can ride along.

The two automatic producers stay coarse by construction. errorInterceptor records failed calls as an endpoint template with numeric and UUID path segments replaced by :id (never query strings or bodies). AuditErrorHandler (core/audit/audit-error-handler.ts) records only an exception’s message and top stack frame, both passed through buildDetails.

The client scrub is a courtesy, not the gate. The BFF re-screens every submitted event server side (AuditPiiScreen) against the same email, SSN-like, Aadhaar-like, and card-like patterns and the same forbidden keys, and drops any event that matches. A tampered client therefore cannot smuggle PII into the audit table. See docs/consumer/features/audit.adoc.

Errors never display raw payloads

errorInterceptor turns every failure into a toast whose text is resolved in strict order. It first tries the BFF’s machine-readable code translated through the i18n catalog, then the BFF’s defaultMessage (a safe, human-written sentence composed server side), then a generic translated fallback. Raw response bodies, stack traces, and HTTP status pages are never rendered, so an upstream error cannot leak internals or reflected input into the UI.

Test coverage

The Playwright end-to-end spec frontend/playwright/tests/registration.spec.ts walks the full registration flow with a known OTP code and a known document key. It then dumps both localStorage and sessionStorage and asserts that neither value appears anywhere in them. This is a regression trap on the "secrets never persist" rule at the point where the client handles its most sensitive input.
