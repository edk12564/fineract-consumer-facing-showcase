Features

This chapter documents each feature module of the BFF. Every module follows the same shape: a bounded context under org.apache.fineract.consumer with command and query sides, described in the architecture chapter. Each section covers the module’s purpose, endpoints, flows, security checks, data model, and test coverage.

Two sections in this chapter cover supporting capabilities rather than user-facing features. The one-time password section describes code issuance and verification, which lives in the shared infrastructure.otp package. The identity section describes the identity match used during registration.

Registration

Purpose

The registration module lets a person who already exists as a client in Fineract Core create consumer credentials on the BFF (backend-for-frontend, the Spring Boot service that sits between the Angular client and Fineract). The flow verifies that the applicant can prove ownership of an identity document already recorded on the Fineract client, sends a one-time password (OTP, a short code delivered out of band) to the applicant’s email address, and, once the OTP is verified, binds a new BFF user account to that Fineract client.

An important clarification: the module does not create a Fineract client. The Fineract client and its identity document must already exist in Fineract Core, for example created by back-office staff during onboarding. Registration provisions the BFF side of the relationship, a row in the BFF users table bound to the existing client_id. The Cucumber suite reflects this: its background step creates the Fineract client through the test harness before any registration call is made.

The OTP verification is itself the second authentication factor. There is no enrolled authenticator such as TOTP; a fresh code is generated per challenge and nothing per-user secret is stored at rest beyond the transient hashed code.

Module layout

The module lives at consumer/src/main/java/org/apache/fineract/consumer/registration and contains only a command side (CQRS, a convention in this codebase where state-changing "command" code and read-only "query" code are kept in separate sub-trees):

  • command/api/RegistrationCommandController: the three REST endpoints.

  • command/service/RegistrationCommandService and RegistrationCommandServiceImpl: orchestration.

  • command/data/*: request, command, and response records for each step.

  • command/exception/IdentityNotVerifiedException: 403 with code error.msg.consumer.registration.identity.not.verified.

The module owns no repository, entity, or Liquibase changeset. It orchestrates two supporting modules, identity (document check against Fineract) and user (persistent account state), plus the shared OTP infrastructure component (infrastructure.otp, challenge issue and validation).

Flow step by step

  1. Submit identity. POST /api/v1/registration/submit carries the Fineract client id, an email address, a password, and an identity document type name plus document key (for example a Passport number). RegistrationCommandServiceImpl.submit:

    1. Calls IdentityQueryService.verifyIdentity, which fetches the client’s recorded identifiers from Fineract Core and compares document type name and normalized key (trimmed, dashes and spaces removed, upper-cased). A mismatch or an unknown client yields a generic IdentityNotVerifiedException; the response does not reveal which field failed.

    2. Hashes the password with the Spring Security PasswordEncoder and calls UserCommandService.create, which inserts a users row in status PENDING_OTP. Duplicate email or duplicate Fineract client id raises UserAlreadyExistsException (409).

    3. Returns the new user’s public UUID as registrationId, status PENDING_OTP, and the masked last four characters of the matched document key.

  2. Send OTP. POST /api/v1/registration/otp/send takes the registrationId and a deliveryMethod string. The service resolves the user, builds an OtpDestination (delivery method plus target address), and calls OtpService.createOtp. Only the email delivery method is implemented; any other value, including sms, is rejected with 400 error.msg.consumer.otp.delivery.method.invalid. The response returns the masked email address, the expiry timestamp, and the time to live in seconds. The code itself never appears in the response.

  3. Verify OTP. POST /api/v1/registration/otp/verify takes the registrationId and the code. OtpService.validateOtp compares the SHA-256 hash of the submitted code with the stored hash and deletes the pending entry on success. The service then calls UserCommandService.markOtpVerified, which transitions the user from PENDING_OTP to BOUND and records bound_at. BOUND means the BFF account is now linked to the Fineract client and can log in. Verifying from any other state raises InvalidBindingStateException (409).

Endpoints

All three endpoints are unauthenticated. SecurityConfig permits /api/v1/registration/** explicitly, and the bearer-token cookie resolver skips these paths so a stale session cookie cannot interfere. The device fingerprint header is not required because the DeviceFingerprintFilter only enforces binding for authenticated (JWT-bearing) requests.

Collaborating modules and Fineract calls

Identity (consumer.identity.query). IdentityQueryServiceImpl is the KYC piece for registration. It injects the generated ClientIdentifierApi (an interface generated from the Fineract OpenAPI spec and implemented by a Feign client, Feign being a declarative HTTP client) and calls retrieveAllClientIdentifiers, which maps to GET /v1/clients/{clientId}/identifiers on Fineract Core. This is the only Fineract call in the registration flow. A Fineract 404 is treated as "no identifiers", which surfaces as the same generic denial as a key mismatch. Any other Feign error becomes IdentityVerificationException (502), so an upstream outage is distinguishable from a failed check.

OTP (consumer.infrastructure.otp). OtpServiceImpl generates a six-character code from digits and upper-case letters using SecureRandom, delivers it, and stores only its SHA-256 hash in Valkey (a Redis-compatible key-value store) under otp:pending:{publicId} with a 300 second TTL. OtpDestination is the channel abstraction: it carries a delivery method and a target, and OtpConstants defines both email and sms names, but createOtp only branches on email and delegates to OtpEmailDeliveryService, which sends a plain-text mail through JavaMailSender (Mailpit in the local Docker stack, institution SMTP in production per application.properties). There is no SMS implementation. OTP issue, failed validation, and attempts-exceeded outcomes are published as structured audit events (OTP_CHALLENGE_ISSUED, OTP_VALIDATION_FAILED, OTP_ATTEMPTS_EXCEEDED).

User (consumer.user). UserCommandService.create and markOtpVerified own the persistent state. The User entity enforces the PENDING_OTP to BOUND transition. The registration module never touches the repository directly.

Failure and abuse handling

  • OTP expiry. The pending hash lives for OtpConstants.OTP_TTL_SECONDS (300 seconds). After expiry the key is gone and validation fails with 400 error.msg.consumer.otp.invalid.

  • Retry limit. Each failed validation increments otp:attempts:{publicId}. On the fifth failure (MAX_OTP_VALIDATION_ATTEMPTS = 5) the pending code is deleted, so further attempts fail even with the correct code, and an OTP_ATTEMPTS_EXCEEDED audit event is published.

  • Replay. Successful validation deletes the pending key, so replaying a consumed code fails. Covered by a dedicated Cucumber scenario.

  • Duplicate registration. UserCommandService.create checks email and Fineract client id up front and also catches the database unique-constraint violation, returning 409 error.msg.consumer.user.already.exists in all three cases. A Fineract client can therefore be bound to at most one BFF user, and an email to at most one account.

  • Enumeration resistance. Identity denial is a single generic 403 regardless of whether the client id, document type, or document key was wrong. The Cucumber suite asserts that the rejection does not reveal which field failed.

  • Secret handling. Codes are hashed with SHA-256 before storage, never logged, and never returned in responses. Document keys are only echoed as the last four characters. Request records use @ToString(onlyExplicitlyIncluded = true) so passwords and document keys do not leak into logs through accidental toString calls.

  • Rate limiting. The infrastructure RateLimitFilter keys its per-user bucket on the JWT subject. Registration requests are unauthenticated, so the filter passes them through unlimited; per-IP throttling is delegated to an upstream edge by design. The OTP attempt counter is the only registration-specific abuse control in the BFF.

  • Delivery failure. A mail-server error surfaces as 502 error.msg.consumer.otp.delivery.failed rather than a silent success.

Design rationale

  • Bind, do not create. Requiring a pre-existing Fineract client with a recorded identity document means the institution controls who may register, and the BFF never writes client data into Fineract during self-registration. Knowledge of the document key acts as the proof of ownership.

  • OTP as the second factor. Mirroring upstream Fineract’s two-factor model, each challenge generates a fresh code and nothing per-user is enrolled. The verify step is a single service call (OtpService.validateOtp), so a WebAuthn factor could be added later without schema changes.

  • Orchestrator over owner. Keeping user rows in consumer.user and codes in infrastructure.otp lets other flows (login two-factor, password change step-up, password reset) reuse the same OTP service and the same account state instead of forking them.

  • Hash-only, TTL-only OTP storage. Storing a SHA-256 hash in Valkey with automatic expiry means a database or cache dump never contains a usable code and expired state cleans itself up.

  • Generic denials. Returning one indistinguishable 403 for every identity mismatch prevents an attacker from confirming which client ids or document values exist.

Limitations and future work

  • SMS delivery is not implemented. OtpConstants names an sms method and OtpDestination is channel-neutral, but OtpServiceImpl.createOtp only handles email and rejects everything else. The abstraction point exists; the SMS provider integration does not.

  • Per-IP throttling is an edge concern. The per-user rate limit filter keys on the authenticated JWT subject, so it does not cover the public registration endpoints; production providers supply per-IP throttling and DDoS protection at their edge, which is not part of the dev stack.

  • No expiry or cleanup for abandoned PENDING_OTP users. A submitted registration that never verifies keeps its email and Fineract client id reserved indefinitely; there is no re-submit path to correct a typo in the email address.

  • Identity verification is equality matching, not a KYC provider. The check compares strings against identifiers already stored in Fineract. There is no pluggable external verifier, no per-region document validation, and the document key is compared in plain form rather than through an encrypted-at-rest verifier port.

Authentication

Purpose

The authentication module signs consumer users in, keeps their session alive, and signs them out. It lives at consumer/src/main/java/org/apache/fineract/consumer/authentication and owns the full session lifecycle: password check, a mandatory one-time password (OTP, a short code delivered out of band) challenge, minting the session tokens, rotating the refresh token, and revoking everything on logout or password change.

Two token kinds are involved. The access token is a short-lived signed JWT (JSON Web Token, a signed claims blob the server can verify without a database lookup). The refresh token is an opaque random value stored hashed in the BFF database and used to mint the next access token. Both are delivered to the browser as HttpOnly cookies, never in a response body. Token claim layout, signing keys, and cookie internals are covered in Tokens in the security chapter; this section only summarizes them.

Module layout

The module is command-only (CQRS convention of this codebase; there is no query side because nothing here is read back by clients):

  • command/api/AuthenticationCommandController: the four REST endpoints under /api/v1/authentication.

  • command/service/AuthenticationCommandService and AuthenticationCommandServiceImpl: all flow logic.

  • command/service/PrincipalUserAuthLookupPort: narrow interface for reading user credentials and binding state. Implemented by user.query.service.PrincipalUserAuthLookupAdapter, so this module never touches the users table directly.

  • command/domain/RefreshToken: JPA entity for the refresh_tokens table.

  • command/repository/RefreshTokenCommandRepository: Spring Data repository (findByTokenHash, findByUserId).

  • command/data/*: commands, request bodies, and response payloads.

  • command/exception/*: InvalidCredentialsException (401), TwoFactorInvalidException (401), RefreshTokenInvalidException (401), AuthenticationKycRevokedException (403).

It delegates to infrastructure components:

  • infrastructure.jwt.service.JwtIssuer: mints ES256-signed JWTs with a random jti, issuer, subject, and caller-supplied claims.

  • infrastructure.access.service.AuthCookieFactory: builds the access_token and refresh_token response cookies.

  • infrastructure.access.service.JwtDenylist: Valkey-backed revocation list for access tokens (by token id and by subject cutoff).

  • infrastructure.kyc.service.ClientStandingChecker: live Fineract client status check (see the KYC section below).

  • infrastructure.otp.service.OtpService: OTP generation, email delivery via SMTP, hashed storage in Valkey, attempt counting.

Login flow

Login is a two-step flow. The password check alone never yields a session; the OTP verification is the second factor and is required on every login.

Figure 2. Login, OTP verify, session mint, and refresh rotation

  1. POST /api/v1/authentication/login carries email and password in the body and the device fingerprint in the X-Device-Fingerprint header. The service looks the user up by email, requires the account to be in BOUND state (bound to a Fineract client, see the registration section), then checks the password with the Spring Security PasswordEncoder. Any failure, unknown email, unbound account, or wrong password, produces the same generic 401 error.msg.consumer.auth.invalid.credentials and publishes a LOGIN_FAILURE audit event. No account lockout counter is kept.

  2. On success the service generates a 6-character OTP, emails it (email is the only implemented delivery method), and stores its SHA-256 hash in Valkey with a 300 second TTL. It then mints a challenge token: a 5 minute JWT whose claims are purpose=2fa_challenge and the caller’s device fingerprint. The response body returns the challenge token, its expiry, and the masked email the code was sent to. This is the only token the module returns in a body rather than a cookie; the client must hold it for step two.

  3. POST /api/v1/authentication/2fa carries the challenge token and the OTP, plus the same X-Device-Fingerprint header. The service decodes the challenge token, verifies the purpose claim and that the fingerprint claim matches the header, then validates the OTP hash. Any failure is 401 error.msg.consumer.auth.two.factor.invalid. On success the OTP is deleted (single use), a session is established (see below), and a LOGIN_SUCCESS audit event is published.

A challenge token can never be used as an access token: the access-token decoder (JwtConfig.accessTokenJwtDecoder) rejects any JWT carrying a purpose claim.

Session establishment and cookies

establishSession in AuthenticationCommandServiceImpl is the single mint path shared by 2FA verify, refresh, and post-password-change reissue. It:

  1. Runs the KYC live check (next section).

  2. Mints an access token (default TTL 15 minutes, authentication.access-token-ttl) with claims tenant, kyc_verified, scope=consumer:full, and device_fingerprint.

  3. Generates a 32-byte random refresh token, stores its SHA-256 hex hash in refresh_tokens together with the device fingerprint and expiry (default TTL 1 day, authentication.refresh-token-ttl), and, when rotating, links the predecessor row to the new one.

The controller converts the result into two Set-Cookie headers built by AuthCookieFactory:

  • access_token: path /api/v1, so it accompanies every API call.

  • refresh_token: path /api/v1/authentication, so it is only ever sent to the authentication endpoints.

Both cookies are HttpOnly, SameSite=Strict, and Secure when authentication.cookie-secure is true (false in the plain-HTTP dev compose stack). Production deployments terminate TLS at their edge and set authentication.cookie-secure=true. The JSON body of a session response contains only the access-token expiry timestamp; raw token values never appear in a body. SecurityConfig reads the access token from the access_token cookie via a custom bearer-token resolver, there is no Authorization header in this API.

Refresh flow

POST /api/v1/authentication/refresh needs the refresh_token cookie and the X-Device-Fingerprint header. The service hashes the presented value and looks the row up by hash. Every rejection is 401 error.msg.consumer.auth.refresh.token.invalid and publishes a REFRESH_TOKEN_REJECTED audit event with a reason detail (token_unknown, revoked, expired, device_mismatch, or rotated_token_replayed).

Rotation. A successful refresh mints a brand-new refresh token and revokes the presented one, recording rotated_to on the old row. Refresh tokens are single use by design.

Grace window. If the presented token has already been rotated, the request is a replay. A replay from the same device within the rotation grace window (default 30 seconds, authentication.rotation-grace-ttl, measured from the moment of rotation) is treated as an honest race, for example two browser tabs refreshing concurrently, and forks a fresh session instead of failing. A replay outside the grace window, from a different device, or of an expired token is treated as theft: every active refresh token of that user is revoked and the request is rejected.

Device binding. The fingerprint stored on the row at issue time must equal the header on the refresh request. A stolen refresh cookie presented from another device fails with device_mismatch, and if the token was already rotated the whole chain is revoked.

Logout and session revocation

POST /api/v1/authentication/logout requires a valid access token (it is not on the public path list). It:

  1. Adds the access token’s jti to the Valkey denylist until the token’s natural expiry plus a 60 second clock-skew pad, so the still-valid JWT stops working immediately.

  2. Revokes the presented refresh token row, if any.

  3. Returns 204 with both cookies expired (Max-Age=0).

The denylist is checked on every authenticated request by a validator inside accessTokenJwtDecoder. If Valkey is unreachable, JwtDenylist fails closed and treats the token as denied.

The service also exposes two internal operations used by the user module’s password flows: revokeAllSessions (password reset: revoke every refresh token and set a subject-level denial cutoff so all previously issued access tokens die) and revokeAllSessionsAndReissue (password change: same, then immediately establish a fresh session for the confirming device).

KYC live check at every mint

kyc_verified is never carried forward from an old token. Every call to establishSession, that is every 2FA verify, every refresh, and every post-password-change reissue, re-checks the bound Fineract client in real time: for a bound user, ClientStandingChecker.isActive issues an uncached Feign call to Fineract Core (GET /clients/{id}) and requires status id 300 (active). A closed or missing client aborts the mint with 403 error.msg.consumer.authentication.kyc.revoked. The check fails closed: a Fineract 404 returns inactive, and any other Fineract error propagates and aborts the mint rather than defaulting to active. The open banking token pipeline applies the same component in OAuth2AccessTokenCustomizer (see the open banking section).

Lockout and abuse handling

  • Credential failures return one generic 401 regardless of cause, so an attacker cannot distinguish unknown email, unbound account, or wrong password. There is no per-account lockout counter for password failures.

  • OTP validation allows at most 5 failed attempts (OtpConstants.MAX_OTP_VALIDATION_ATTEMPTS); on the fifth the pending code is deleted, forcing a fresh login, and an OTP_ATTEMPTS_EXCEEDED audit event is published. Codes expire after 300 seconds and are stored only as SHA-256 hashes.

  • A replayed rotated refresh token outside the grace window revokes the user’s entire refresh-token chain.

  • Per-user rate limiting (RateLimitFilter.perUser, default 300 requests per minute, keyed by the JWT subject) sits on the same filter chain but only bites on authenticated requests. The unauthenticated login, 2FA, and refresh endpoints are not rate limited inside the BFF; by project policy, per-IP volumetric limiting is delegated to an upstream edge service.

  • Security-relevant events are published to the audit module: LOGIN_SUCCESS, LOGIN_FAILURE, REFRESH_TOKEN_REJECTED (with reason), DEVICE_FINGERPRINT_MISMATCH, and the OTP events. OTP values themselves are never logged or audited.

Two quirks worth knowing:

  • AuthenticationClient is built on core Feign (Feign.builder() with @RequestLine) instead of the usual @FeignClient, because the test must read the rotating Set-Cookie response headers, which a typed @FeignClient method discards. Design rationale

  • Cookies over header tokens. Both tokens live in HttpOnly SameSite=Strict cookies, so scripts cannot read them and browsers do not attach them to cross-site requests. The refresh cookie is additionally path-scoped to /api/v1/authentication, keeping the long-lived credential off every ordinary API call. CSRF protection (csrf().disable() in SecurityConfig) relies on this SameSite=Strict posture plus the mandatory custom X-Device-Fingerprint header, which a cross-site form post cannot supply.

  • OTP as the second factor, per challenge. Mirroring upstream Fineract’s 2FA model, nothing per-user is enrolled or stored at rest; a fresh code is generated and hashed for each login. The stateless challenge token carries the flow between the two steps without server-side session state, and its purpose claim plus the decoder-side rejection of purposed tokens keeps it single-purpose.

  • Hashed, rotating, device-bound refresh tokens. Storing only the SHA-256 hash means a database leak does not yield usable tokens. Single-use rotation with a linked rotated_to chain makes theft detectable: a replay after rotation is distinguishable from first use, and cross-device replay evidence triggers full-chain revocation. The short same-device grace window is a deliberate concession to concurrent browser tabs.

  • One mint path. Login, refresh, and password-change reissue all converge on establishSession, so the KYC live check and the claim set cannot drift between entry points. The check is uncached and fail-closed on purpose: a consumer whose Fineract client was closed loses the ability to mint anything within one access-token TTL, at the cost of one Fineract round trip per mint.

  • Denylist over short-token-only revocation. Access tokens are stateless, so logout and revoke-all need the Valkey denylist (per-jti and per-subject cutoff) to take effect before natural expiry. Failing closed when Valkey is down trades availability for the guarantee that a revoked token is never accepted.

Limitations and future work

  • Password-step throttling is an edge concern. The per-user limiter applies only to authenticated requests; production providers supply per-IP throttling and DDoS protection at their edge, which is not part of the dev stack.

  • Email is the only OTP channel. The OtpDestination abstraction anticipates SMS, but only the email delivery method is implemented; anything else is rejected.

  • No remembered-device or step-down option. Every login requires an OTP round trip, even from a device that completed one minutes earlier.

  • The device fingerprint is client-asserted. It is an opaque value the client sends (the demo frontend uses a locally stored UUID). It binds tokens to a device identifier but is not proof of possession; an attacker who exfiltrates both the cookie and the fingerprint value can replay them.

  • refresh_tokens rows are never purged. Revoked and expired rows accumulate; unlike the audit tables there is no retention job for this table.

  • No user-facing session management. revokeAllSessions is only reachable through the password flows; there is no endpoint to list or revoke other sessions.

One-Time Passwords

The OTP code is not a feature module. It lives in the infrastructure module at consumer.infrastructure.otp. This section is kept in the features chapter for discoverability; the code it describes is infrastructure.

Purpose

The OTP capability issues and verifies one-time passwords (OTP, a short code delivered out of band and valid for a single use). It is a supporting capability, not a user-facing feature: it exposes no REST controllers and owns no endpoint. Feature modules call its service whenever a flow needs proof that the caller controls the registered email address. Five modules depend on it: registration (binding a new BFF account), authentication (the second factor at login), user (password change and password reset), transfers (step-up confirmation before moving money), and beneficiaries (step-up confirmation before adding or updating a payee).

The OTP is the codebase’s only challenge factor. There is no enrolled authenticator such as TOTP; a fresh code is generated per challenge and nothing per-user secret persists beyond the transient hashed code.

Code layout

The code lives at consumer/src/main/java/org/apache/fineract/consumer/infrastructure/otp. As an infrastructure sub-package it has no CQRS command/ or query/ split (infrastructure is side-agnostic); it follows the infrastructure convention of data/ for value objects and constants, service/ for behavior:

  • service/OtpService and OtpServiceImpl: the public contract, createOtp and two validateOtp overloads.

  • service/OtpEmailDeliveryService: sends the code by email through JavaMailSender (Spring’s SMTP client abstraction).

  • data/OtpConstants, OtpDestination, OtpMetadata, PendingOtp: constants and value objects.

  • repository/OtpRepository: Valkey (a Redis-compatible key-value store) persistence via StringRedisTemplate.

  • exception/*: OtpTokenInvalidException (400, error.msg.consumer.otp.invalid), OtpDestinationInvalidException (400, error.msg.consumer.otp.delivery.method.invalid), OtpDeliveryFailedException (502, error.msg.consumer.otp.delivery.failed).

Generation, hashing, and storage

OtpServiceImpl.createOtp generates a six-character code drawn from a 36-character alphabet (digits 0-9 and upper-case A-Z) using a shared SecureRandom instance. The raw code is handed to the delivery service and then discarded; only its hash is stored.

The hash is an unsalted SHA-256 digest of the upper-cased code, hex-encoded. Upper-casing before hashing makes validation case-insensitive, so a user may type a1b2c3 for a delivered A1B2C3. There is no salt or keyed MAC; see the limitations section.

Storage is Valkey only. The OTP code owns no Liquibase changeset and no PostgreSQL table.

Verification, TTL, and attempt limits

validateOtp(publicId, token) fetches the stored hash, hashes the submitted token, and compares. On success it deletes both keys, making every code single use; the Cucumber suites assert that replaying a verified code is rejected. On failure:

  • If a pending hash exists, the attempts counter is incremented. At MAX_OTP_VALIDATION_ATTEMPTS (5) failures both keys are deleted, so the pending code is burned and the caller must request a new one.

  • The failure is published as an audit event: OTP_ATTEMPTS_EXCEEDED when the cap is hit, otherwise OTP_VALIDATION_FAILED. Successful issue publishes OTP_CHALLENGE_ISSUED. Event details carry only the user’s public UUID, never the code.

  • The supplied exception is thrown. The default overload throws OtpTokenInvalidException; the second overload takes a Supplier so each caller surfaces its own flow-specific error (TwoFactorInvalidException for login, TransferStepUpInvalidException for transfers, and so on) without revealing that an OTP subsystem exists. TwoFactorInvalidException responds with HTTP 401; the Angular error interceptor treats a 401 that carries an application error code as a flow error rather than an expired session, so a wrong login OTP does not log the user out.

The time to live is OtpConstants.OTP_TTL_SECONDS (300 seconds, 5 minutes), enforced by Valkey key expiry rather than application code. Both the TTL and the attempt cap are compile-time constants, not configuration properties.

There is no resend cooldown. Neither the OTP code nor any caller throttles how often createOtp may be invoked; a resend simply overwrites the pending key and resets the attempts counter. This is deliberate separation of concerns: per-user request throttling belongs to the infrastructure RateLimitFilter (300 requests per user per minute, consumer.rate-limit.per-user-per-minute), which keys on the authenticated JWT subject and is independent of the OTP attempt counters. That filter skips unauthenticated requests; for the public registration OTP-send and forgot-password endpoints, production providers supply per-IP throttling and DDoS protection at their edge, which is not part of the dev stack.

Delivery channels

OtpDestination is the channel abstraction: a delivery method name plus a target address. OtpConstants names two methods, email and sms, but createOtp only branches on email (case-insensitive) and rejects everything else, including sms, with OtpDestinationInvalidException. There is no SMS implementation and no delivery-port interface; email is wired directly.

OtpEmailDeliveryService sends a plain-text SimpleMailMessage containing the code and a hardcoded "expires in 5 minutes" line. Delivery is real SMTP, not a stub: the local Docker stack routes it to Mailpit (a development SMTP server with an HTTP API, axllent/mailpit in consumer/compose.yaml), and production is expected to point spring.mail.host at institution SMTP. A MailException becomes OtpDeliveryFailedException (502) so callers can distinguish an outbound-mail outage from a bad request.

Design rationale

  • Hash at rest, store nothing durable. Keeping only a SHA-256 hash in a TTL-bound Valkey key means a database dump contains no OTP material and expiry needs no scheduled cleanup. Valkey was already in the stack for the JWT denylist, so no new infrastructure was added.

  • One service, many flows. Login 2FA, registration, password reset, and every step-up challenge share a single issue-and-verify pipeline, so hardening (attempt caps, audit events, single use) applies uniformly instead of being reimplemented per feature.

  • Caller-supplied exceptions. The Supplier overload lets each flow return its own generic error code, so API responses do not leak which internal check failed.

  • Per-user key, not per-flow. Keying on the public UUID keeps the store simple and guarantees at most one live code per user, at the cost of the cross-flow replacement behavior noted below.

  • Counters separate from rate limiting. OTP attempt counters guard guessing of a specific code; the infrastructure RateLimitFilter guards request volume. They are deliberately independent mechanisms with independent storage.

Limitations and future work

  • No SMS channel. The sms constant exists but any non-email destination is rejected. Adding SMS means adding a branch in createOtp and a new delivery service; there is no delivery-port interface to implement against.

  • Unsalted SHA-256 over a small keyspace. A six-character, 36-symbol code has about 2.2 billion combinations, which is trivially brute-forceable offline if the Valkey store leaks. The 300-second TTL and single-use semantics limit the window, but a keyed hash (HMAC) would remove the offline-guessing concern.

  • No resend cooldown. Repeated createOtp calls each send a mail and reset the attempts counter. Authenticated callers are bounded only by the general 300-per-minute filter; the unauthenticated registration and forgot-password entry points have no BFF-side throttle and depend on upstream edge protection.

  • Cross-flow replacement. Because the pending key is per user, requesting a transfer step-up code invalidates a pending login or password-reset code for the same user. Harmless in practice but surprising; a per-purpose key component would remove the interaction.

Identity Verification

Purpose

Identity verification, commonly called KYC (know your customer, the regulatory requirement to confirm who a customer is), gates access to the consumer banking surface. A consumer may only register a BFF account against a Fineract client record if they can present the government ID that the bank already holds on that record. Until a user completes verification and OTP binding, tokens minted for them carry kyc_verified=false and the ABAC layer denies almost every action.

The BFF does not call an external KYC provider. Verification is a possession check: the applicant submits an ID type and number, and the BFF matches them against the client identifiers already stored in Fineract Core by the back office. The assumption is that the back office vetted the physical document when it created the Fineract client; the BFF only proves that the person registering knows that document.

Division of responsibility

The feature spans three packages.

consumer.identity (query side only)

Owns the matching logic. IdentityQueryService is the port interface (a small Java interface that the rest of the codebase depends on, so the implementation can be swapped without touching callers). The single implementation, IdentityQueryServiceImpl, fetches all identifiers for a Fineract client and compares them against the submitted document. There is no controller and no command side: verification does not mutate any state, and no endpoint exposes it directly.

consumer.registration (command side)

Owns submission. ID numbers enter the system in exactly one place: the request body of POST /api/v1/registration/submit (documentTypeName and documentKey fields on SubmitRegistrationCommandRequest). RegistrationCommandServiceImpl.submit builds an IdentityVerificationQuery, calls IdentityQueryService.verifyIdentity, and only creates the BFF user row if the result is verified. The document key is used in memory for the comparison and is never persisted by the BFF.

consumer.infrastructure.kyc

Owns the ongoing standing check. ClientStandingChecker.isActive(fineractClientId) fetches the client from Fineract and returns true only when the client status id is 300 (active). It returns false on 404 and lets any other Feign error propagate, so token minting fails closed when Fineract is unreachable.

Matching logic

IdentityQueryServiceImpl.verifyIdentity:

  1. Calls the generated Feign client ClientIdentifierApi.retrieveAllClientIdentifiers(clientId), which maps to Fineract’s GET /v1/clients/{clientId}/identifiers.

  2. Filters identifiers whose document type name equals the submitted documentTypeName.

  3. Normalizes both the stored and submitted keys (trim, strip hyphens and spaces, uppercase) and requires an exact match.

  4. On a match, returns IdentityVerificationQueryData.verified(lastFour) where lastFour is the last four characters of the normalized key (null if the key is shorter than four characters). Otherwise returns denied().

A 404 from Fineract is treated as "no identifiers", so it produces a denial rather than an error. Any other Feign failure is wrapped in IdentityVerificationException (HTTP 502, code error.msg.consumer.identity.verification.unavailable) so an upstream outage is distinguishable from a mismatch.

Pluggable ID types

There are no per-region verifier classes. ID types are data, not code: each type is a Fineract code value under the Customer Identifier code (m_code_value in Fineract Core). The matching logic is type agnostic string comparison, so adding PAN, passport, or any other document type requires only adding a code value in Fineract and attaching an identifier of that type to the client. No BFF change is needed.

This is exercised in practice: consumer/scripts/seed-demo.sh seeds SSN and Aadhaar code values, while the Cucumber registration suite uses a Passport identifier that exists nowhere in BFF source. All three work through the same path.

The tradeoff is that there is no type specific validation (no SSN format check, no Aadhaar Verhoeff checksum). Whatever string the back office stored is the truth.

Security handling

ID numbers are never stored by the BFF

The BFF schema contains no identifier column anywhere (see the data model below); the document key exists only in memory during the submit request. Consequently there is no encrypting AttributeConverter for ID numbers: there is nothing at rest to encrypt. The only AttributeConverter implementations in the codebase are the open banking permission set converters. The identifier at rest lives in Fineract Core (m_client_identifier), under Fineract’s own storage model.

ID numbers are never logged

SubmitRegistrationCommandRequest, SubmitRegistrationCommand, and IdentityVerificationQuery are all annotated @ToString(onlyExplicitlyIncluded = true) with no included fields, so an accidental log of the object prints no field values. No log statement in the identity or registration path emits the key.

ID numbers are never returned

The submit response (SubmitRegistrationCommandData) carries registrationId, status, and maskedLastFour only. The internal result (IdentityVerificationQueryData) carries verified plus maskedLastFour only.

Mismatches do not leak which field failed

A failed match raises IdentityNotVerifiedException (HTTP 403, code error.msg.consumer.registration.identity.not.verified, message "registration could not be completed"). The Cucumber suite asserts that the rejection does not reveal whether the type or the key was wrong.

Result flow and audit trail

Fineract holds the durable facts: the identifier record and the client status. The BFF holds only the registration outcome on the users row: status moves from PENDING_OTP (identity matched, user created) to BOUND (OTP verified), with bound_at recording when. kyc_verified is derived from this at every token mint: the user must be BOUND and ClientStandingChecker must confirm the Fineract client is still active.

The structured audit log (audit_events) records the surrounding flow: OTP_CHALLENGE_ISSUED, OTP_VALIDATION_FAILED, OTP_ATTEMPTS_EXCEEDED from the OTP service, and ACCESS_DENIED with reason kyc_required when the ABAC layer blocks an unverified user. There is no dedicated audit event for the identity match itself; a failed submit is observable only through the HTTP response.

Downstream consumption of kyc_verified

kyc_verified is a JWT claim (JwtClaims.KYC_VERIFIED). It is stamped at every mint, never carried forward:

  • Consumer login and refresh: AuthenticationCommandServiceImpl.establishSession passes the user’s bound state as kycVerified, and when it is true it live checks ClientStandingChecker.isActive. A closed or missing client raises AuthenticationKycRevokedException (HTTP 403, code error.msg.consumer.authentication.kyc.revoked).

  • Open banking mints: OAuth2AccessTokenCustomizer.stampKycVerified runs on authorization code and refresh token grants. It stamps the claim only for bound users, and throws an invalid_grant OAuth2 error if the standing check fails. Transport failures propagate, so the mint fails closed.

  • Enforcement: AccessPolicyEvaluator denies any action whose policy requires KYC when the claim is not true, publishing ACCESS_DENIED with reason kyc_required. Only a small set of actions (USER_PROFILE_VIEW, USER_IMAGE_VIEW, USER_PASSWORD_CHANGE, AUDIT_EVENT_SUBMIT, and the open banking TPP consent actions) are exempt.

  • Surface: GET /api/v1/user/profile echoes the claim back to the Angular client as kycVerified.

Token structure, minting, and the fail closed rules are documented in Tokens; this section does not duplicate them.

Design rationale

  • Matching against bank held records instead of integrating an external verifier keeps the trust anchor where it already is: the back office created the identifier after inspecting the document. The BFF only proves possession of that knowledge.

  • Storing nothing is the strongest at rest protection. There is no encrypted column to rotate keys for, no backup exposure, and no deletion obligation, because the sensitive value never touches the BFF database.

  • ID types as Fineract code values makes new document types (PAN, passport) purely additive configuration. The Cucumber suite proving Passport works without code changes is the design working as intended.

  • The identity module is query only by construction: verification reads Fineract state and returns a value object. Persisting the outcome belongs to registration, which owns the user lifecycle.

  • Deriving kyc_verified fresh at every mint, backed by a fail closed standing check, means a client closed in Fineract loses consumer access within one access token TTL, without any revocation plumbing in the BFF.

Limitations and future work

  • Verification is a matching check, not document verification. There is no external KYC provider integration, no liveness or document capture, and no type specific validation (an SSN with an impossible format passes if the back office stored it that way).

  • Submit-endpoint throttling is an edge concern. The per user RateLimitFilter does not apply to the public submit endpoint; production providers supply per IP throttling and DDoS protection at their edge, which is not part of the dev stack.

Savings

Purpose

The savings module provides read-only consumer views of a customer’s savings accounts: the account list, account detail with balances, account charges, and transaction history. It is a query-only module. There is no command side: the BFF (backend-for-frontend, the Spring Boot service that sits between the Angular client and Fineract Core) does not create or mutate savings accounts through this module. Deposits and withdrawals initiated by the consumer are handled by the transfers feature, not here.

Code lives under consumer/src/main/java/org/apache/fineract/consumer/savings/query/, following the project CQRS layout (CQRS: commands and queries are separated end to end). Only the query sub-tree exists.

All endpoints are served by SavingsQueryController under the base path /api/v1/savings and return JSON. Ownership and ABAC checks

Every service method calls AccessPolicyEvaluator.authorize(…​) (in consumer.infrastructure.access) before any Fineract call. The evaluator checks, in order: a policy exists for the action, the JWT scope claim intersects the policy’s allowed scopes, the kyc_verified claim is true, and, for owned actions, the caller owns the resource. Any failure publishes an ACCESS_DENIED audit event and throws; ownership denials on savings throw SavingsQueryAccessDeniedException (HTTP 403, code error.msg.consumer.savings.query.access.denied).

Ownership works as follows. UserClientResolver maps the JWT subject (the BFF user’s public UUID) to the bound Fineract client id via a database lookup. OwnedAccountsCache then resolves the set of savings and loan account ids that client owns by calling Fineract GET /v1/clients/{clientId}/accounts, cached in a two-level cache (in-process Caffeine, 60 second TTL, backed by Valkey, 300 second TTL). The requested savingsId must be in that set. A savingsId the caller does not own is rejected at the BFF; the request never reaches Fineract.

The list endpoint has no per-resource check because it is scoped by construction: the service resolves the caller’s own client id and asks Fineract only for that client’s accounts.

See Attribute-Based Access Control (ABAC) for the general policy model, the policy table, and the caching and eviction rules.

DTO mapping policy

Fineract response shapes never pass through to the Angular client. Each operation maps the generated Fineract model into a module-owned read model in savings/query/data/: SavingsAccountListItemQueryData, SavingsAccountQueryData, SavingsChargeQueryData, SavingsTransactionQueryData, SavingsApplicationTemplateQueryData, and SavingsProductOptionQueryData, plus the page envelope SavingsTransactionQueryResponse. Mapping is a deliberate subset: only the fields the consumer UI needs are carried over.

Fineract’s enum-option objects ({id, code, value} triples for status and transaction type) are flattened to their stable code string (for example savingsAccountStatusType.active); the localized display value is not exposed. Account read models additionally carry a boolean active flag derived from the status object. The application template detail exposes each enum setting as an id and code pair (for example interestCompoundingPeriodTypeId and interestCompoundingPeriodTypeCode). Currency objects are reduced to the currency code. Monetary and rate fields (balance, availableBalance, amount, runningBalance, amountOutstanding, nominalAnnualInterestRate) are java.math.BigDecimal end to end; no floating-point types touch money. Dates are java.time.LocalDate.

BFF state

The module stores nothing. There is no repository/ or domain/ package, no JPA entity, and no Liquibase changeset for savings. Every read is a live pass-through to Fineract. The only state involved is the ownership cache described above, which is infrastructure owned by the access package, not by this module.

Design rationale

  • Query-only by design. Consumer-initiated money movement belongs to the transfers feature, and account opening is not offered, so a savings command side would be an empty shell. Per project convention, absent sides are not pre-created.

  • Ownership is enforced at the BFF, before Fineract is called. Fineract’s own authorization is back-office shaped and is not trusted as the consumer policy enforcement point. Failing early also avoids leaking existence information about other clients' accounts.

  • The service is exposed as an interface (SavingsQueryService) so the open banking module can reuse the exact same read path under a narrower token scope instead of forking a second savings client. The ABAC action table, not the module, decides which scopes may invoke each operation.

  • Thin DTOs keep the Angular client decoupled from Fineract’s large response shapes and prevent accidental exposure of upstream fields that were never reviewed for consumer visibility.

Limitations and future work

  • Only date and sort filters are exposed. Fineract’s transaction search supports filtering by amount range, transaction type, and submitted date; the BFF exposes only fromDate, toDate, and sort. Additional filters would be additive parameters on the existing endpoint.

  • No statement document generation (PDF or export). "Statements" today means the filterable transaction list.

  • Ownership checks read a cached account set. The cache uses 60 s / 300 s TTLs, so an account added to a client mid-session may be denied until the cache entry expires or is evicted.

Loans

The loans module (org.apache.fineract.consumer.loans) gives a logged-in consumer a view of their loan accounts and lets them apply for a loan. It follows the repository’s CQRS convention (CQRS: reads and writes are modeled as separate code paths). The query side serves loan reads: account list, account detail with outstanding balance, repayment schedule preview, transactions, charges, guarantors, and the loan product catalog. The command side serves loan application writes: submit, modify, and withdraw.

The module holds no state of its own. Every request is authorized in the BFF (backend-for-frontend: the intermediary service the browser talks to instead of Fineract) and then delegated to Apache Fineract, which is the system of record for all loan data. There is no separate products module in the codebase; the loan product catalog is served from this module through the application template endpoint. Savings products are served by the savings module.

Query endpoints

All endpoints are rooted at /api/v1/loans (LoansQueryController). Every endpoint requires an authenticated JWT (JSON Web Token: the signed access token issued at login); anonymous requests receive 401. On top of authentication, each service method runs an ABAC check (ABAC: attribute-based access control, authorization decided from attributes of the caller and the resource) through AccessPolicyEvaluator. All loan actions require the kyc_verified claim on the token.

Loan application lifecycle

The BFF persists no application state; the lifecycle lives entirely in Fineract.

  • There is no server-side draft. An unsubmitted application exists only as form state in the client. The "draft" the consumer can still edit is the Fineract loan application in status loanStatusType.submitted.and.pending.approval, which is what POST /api/v1/loans creates upstream.

  • Modify (PUT) and withdraw (POST ?command=withdrawnByApplicant) act on that pending application. Fineract enforces which transitions are legal for the current status; the BFF translates upstream rejections to LoanApplicationInvalidException (400).

  • Withdrawal moves the application to loanStatusType.withdrawn.by.client. Approval, rejection, and disbursement are back-office operations performed in Fineract; the BFF exposes no endpoints for them.

  • Status is tracked by reading, not by callback: the list and detail endpoints pass through Fineract’s status code string (loanStatusType.submitted.and.pending.approval, loanStatusType.approved, loanStatusType.active, loanStatusType.withdrawn.by.client, loanStatusType.rejected, loanStatusType.closed.obligations.met, and the other values of Fineract’s LoanStatus enum).

  • The only local side effect of a submit is a cache eviction: LoansCommandServiceImpl evicts the caller’s entry in OwnedAccountsCache so the new loan passes ownership checks immediately instead of after the cache TTL.

Access control and idempotency

Authorization is centralized in AccessPolicyEvaluator with the policy table in ActionPolicies (consumer.infrastructure.access). For each action it checks, in order: a policy exists, the token carries an allowed scope, the kyc_verified claim is true (required for every loan action), and, for per-loan actions, that the loan id belongs to the caller. Ownership is resolved from OwnedAccountsCache, a two-level cache (in-process Caffeine, 60 second TTL, backed by Valkey, 300 second TTL) populated from Fineract’s GET /v1/clients/{clientId}/accounts. Denials are published as ACCESS_DENIED audit events and surface as 403 with the codes error.msg.consumer.loans.query.access.denied or error.msg.consumer.loans.command.access.denied. See Attribute-Based Access Control (ABAC) for the full policy model.

For idempotency, the controller validates the raw Idempotency-Key, and the command service derives a per-user key (IdempotencyKeyDeriver, SHA-256 of user public id plus raw key) and places it in the request-scoped IdempotencyKeyHolder, from which a Feign interceptor forwards it to Fineract. Fineract performs the replay detection: a repeated key returns the original result, and a replay that arrives while the original request is still executing is translated to LoanCommandInProgressException (425 Too Early, error.msg.consumer.loans.request.in.progress). See Idempotency for the derivation and interceptor details.

Design rationale

  • Stateless passthrough. Fineract is already the system of record for loans; persisting application state in the BFF would create a dual-write problem for no consumer-visible gain. The BFF’s value here is authorization, DTO translation, and idempotency plumbing.

  • Product catalog folded into the template endpoint. This mirrors Fineract’s own template convention (GET /v1/loans/template), where one endpoint serves both the browse list and the per-product defaults a client needs to build an application form, so a separate products module was not created.

  • Schedule preview on the query side. Fineract models preview as POST /loans?command=calculateLoanSchedule on the same resource as submit. The BFF separates them: preview creates nothing, so it belongs to the query side, and giving it its own path (/schedule-preview) keeps the submit endpoint free of a mode switch.

  • Ownership enforced in the BFF. Fineract’s deprecated self-service layer used to scope data to the caller; with the BFF as the only Fineract client, the caller-to-loan check must happen here, before any upstream call, which is why every {loanId} endpoint runs the owned-resource policy.

  • Per-side exception sets with stable error codes (error.msg.consumer.loans.*) let API clients branch on machine-readable codes rather than messages, consistent with the repository-wide exception convention.

Limitations and future work

  • No server-side draft. An application form abandoned before submit is lost with the browser session; supporting resumable drafts would require the module’s first BFF table.

  • Transaction date filtering happens in the BFF. Fineract’s loan transaction API has no date parameters, so a date-filtered request fetches up to 10,000 transactions in one upstream call and filters in memory; a loan with more transactions than that would return a truncated result, and each filtered request re-fetches the full set.

  • Statuses are raw Fineract code strings. Clients must know the upstream vocabulary (loanStatusType.*); the BFF adds only a boolean active convenience flag and does not translate the codes into a consumer-facing status enum.

  • Template browse carries only product id and name. A client must fetch each product individually to compare terms.

Transfers

The transfers module moves money out of a customer’s own savings account and serves the customer’s transfer history. It supports three destination cases through a single initiate/confirm endpoint pair: another savings account the customer owns, a saved beneficiary’s savings account, and one of the customer’s own loan accounts. A loan repayment is not a separate feature: it is a transfer whose destination type is loan, executed upstream through the same Fineract account-transfers API, and it is restricted to loans the caller owns; the demo UI surfaces it from the loan detail page rather than the transfers page. The BFF (backend-for-frontend, the Spring Boot service that sits between the Angular client and Fineract Core) validates, authorizes, and challenges the request; Fineract Core performs the actual accounting.

Code lives in org.apache.fineract.consumer.transfers, following the repository’s CQRS layout (Command Query Responsibility Segregation, the project convention of splitting write-side and read-side code into separate trees): the command side handles the initiate and confirm flow, and the query side serves transfer history.

All endpoints live under /api/v1/transfers and are registered as authenticated() in SecurityConfig (/api/v1/transfers/**), so they require a valid consumer access token (a JWT, a signed JSON Web Token issued by the BFF’s own auth stack). Every request must also pass the device-fingerprint filter that applies to all authenticated routes, so the X-Device-Fingerprint header is required on the history endpoint as well as the command endpoints.

Transfer flow

initiate runs these steps in TransfersCommandServiceImpl:

  1. Resolve the destination type (savings or loan).

  2. Authorize ConsumerAction.TRANSFER_EXECUTE against the source account through AccessPolicyEvaluator.

  3. Check the destination is allowed (own loan, registered savings beneficiary, or owned savings account; see below).

  4. Create an email OTP through the infrastructure.otp module.

  5. Issue a step-up token with a 5 minute TTL (StepUpConstants.STEPUP_TTL), bound to the user, the device fingerprint, and an action fingerprint: a SHA-256 hash of endpoint|fromAccountId|toAccountId|accountTypeCode|amount computed by StepUpTokenService. The amount is normalized with stripTrailingZeros() before hashing so 10.0 and 10.00 fingerprint identically.

confirm recomputes the action fingerprint from the submitted body and verifies the step-up token against it. Changing any parameter between initiate and confirm (source, destination, type, or amount) produces a different fingerprint and the token is rejected with HTTP 401 (TransferStepUpInvalidException). It then validates the OTP, re-runs the same authorization and destination checks as initiate, resolves office and client ids from Fineract, and posts the transfer upstream. For a loan destination the destination client and office are the caller’s own, since only the caller’s loans are permitted; for a savings destination the owning client and office are resolved from Fineract.

Transfer history flow

The history endpoint covers savings-to-savings transfers only; savings-to-loan transfers are excluded because repayments belong to the loan account view served by the loans module. TransfersQueryServiceImpl.listTransfers runs these steps:

  1. Authorize ConsumerAction.TRANSFER_LIST (no resource id; the policy requires the consumer:full scope and a true kyc_verified claim).

  2. Resolve the caller’s Fineract client id through UserClientResolver and list the client’s savings accounts (ClientApi.retrieveAllClientAccounts).

  3. For each savings account, authorize SAVINGS_VIEW; a denial fails the whole request with HTTP 403 (TransferQueryAccessDeniedException). Then fetch the account with its transactions (SavingsAccountApi.retrieveSavingsAccount with the transactions association) and collect every transaction that carries a transfer reference, keyed by transfer id so the two legs of a transfer between two owned accounts merge into one row. A withdrawal leg sets the source account number; any other leg sets the destination.

  4. For transfers whose destination leg was not found among the caller’s savings accounts, fetch the transfer detail (AccountTransfersApi.retrieveOne6, GET /v1/accounttransfers/{transferId}). If the upstream destination account type id is 1 (loan), the row is dropped; otherwise the counterparty savings account number is taken from the detail and zero-padded to 9 digits to match Fineract’s display format.

  5. Filter by the optional date range, sort newest first (transfer date descending, then transfer id descending), and page in the BFF over the materialised set, which is why the response carries an exact total.

A row’s direction is OUTGOING when a withdrawal leg on one of the caller’s accounts was found, otherwise INCOMING. Any upstream failure is translated to HTTP 502 (TransferQueryUpstreamUnavailableException). The cost grows with the caller’s account count (N+1 Fineract calls) plus one extra call per transfer whose counterparty leg is outside the caller’s savings accounts; nothing is cached or persisted.

Money handling

Amounts are BigDecimal from the request body through to the upstream call; no floating-point types appear anywhere in the module. Bean Validation enforces @NotNull @Positive on the amount and both account ids. The amount is serialized to Fineract with toPlainString() (no scientific notation) alongside a fixed en locale and yyyy-MM-dd date format. The transfer date is the BFF server’s current date (LocalDate.now()), and the description is the constant "Consumer initiated transfer". The BFF does not carry or validate a currency field; currency compatibility between the two accounts is enforced by Fineract Core.

Data model

The module owns no BFF tables. There is no transfers directory under db/changelog, no JPA entity, and no repository. Design rationale

The two-phase initiate/confirm design keeps the BFF stateless about pending transfers. Instead of persisting a draft transfer row, the step-up token carries a hash of the exact transfer parameters, so the confirm request proves both possession of the challenge and that the parameters did not change. This avoids a table, a cleanup job, and a class of stale-draft bugs.

All authorization checks run twice, once per phase. Confirm cannot trust that initiate ran its checks because account ownership, beneficiary status, or KYC state can change between the two calls, and because confirm is an independent HTTP request that must stand on its own.

Idempotency is delegated to Fineract rather than deduplicated in a BFF table because Fineract is the system of record for the money movement; a BFF-side dedupe could disagree with upstream reality after a partial failure. Deriving the forwarded key from the user id prevents one user’s key from colliding with, or probing, another’s.

The query side owns transfer history because it is a cross-account view: per-account transaction lists already belong to the savings and loans modules, but a single list of the customer’s transfers spans accounts and needs transfer-specific leg merging. It reads Fineract directly instead of persisting a BFF-side transfer log because Fineract is the system of record; a BFF copy could diverge after partial failures. Savings-to-loan transfers are excluded from the history because repayments are presented on the loan account view; including them here would duplicate the loan module’s transaction history.

Limitations and future work

  • Transfers execute immediately. They use the server’s current date; there is no scheduling, no future-dated transfer, and no recurring transfer.

  • The transfer description is a fixed constant. The customer cannot attach a note.

  • No amount ceiling on own-account transfers. Transfers to the customer’s own accounts are bounded only by the optional per-beneficiary transferLimit. A global or per-tier transaction limit would need new policy data.

  • The OTP channel is hard-coded to email. This applies to the transfer step-up flow.

Beneficiaries

The beneficiaries module (org.apache.fineract.consumer.beneficiaries) manages saved payees: destination accounts a customer registers once and can then transfer money to. A beneficiary points at another Fineract client’s savings account; loan beneficiaries are not supported, so third-party loan repayment is not possible. The module follows the repository’s CQRS layout (CQRS: commands that change state and queries that read state are kept in separate subtrees with their own controllers, services, entities, and repositories): command/ handles add, update, and delete; query/ handles listing.

Beneficiary records are the allow-list for outbound transfers to accounts the customer does not own. The transfers module refuses any savings destination that the caller does not own and has not registered as an active beneficiary; loan destinations are limited to the caller’s own loans and never consult beneficiaries.

Lifecycle

Adding and updating are two-phase flows with a step-up challenge. There is no cooling-off period and no separate verify or activate state: a beneficiary is active immediately after confirm, and a soft delete takes effect immediately.

Initiate. The service authorizes the ABAC action, rejects duplicate names (case-insensitive among the caller’s active beneficiaries), and resolves the destination savings account against Fineract: SearchApiApi.searchData with resource savings, then SavingsAccountApi.retrieveSavingsAccount to confirm the exact account number.

The resolved account must be in a non-closed upstream status (SavingsAccountStatusType ids 100, 200, 300, 303, 304: submitted-and-pending, approved, active, transfer-in-progress, transfer-on-hold). As a knowledge check, the caller must also supply the office name of the account holder; the service loads the owning client via ClientApi.retrieveOneClient and rejects the request if the office name does not match. The account must also belong to a different Fineract client: registering one of the caller’s own accounts fails with HTTP 400 and code error.msg.consumer.beneficiaries.command.account.self (BeneficiarySelfAccountException), because transfers to own accounts go through the ownership check instead. Any other resolution failure maps to HTTP 400 with code error.msg.consumer.beneficiaries.command.account.invalid; upstream outages map to HTTP 502.

If validation passes, the service sends an OTP to the caller’s registered email (delivery is email only) and issues a step-up token: a 5 minute JWT (StepUpConstants.STEPUP_TTL) bound to the caller’s subject, the X-Device-Fingerprint header value, and an action fingerprint, a SHA-256 hash of the exact request parameters (name, office name, account number, transfer limit). OTPs are stored hashed, expire after 300 seconds, are single use, and allow at most 5 validation attempts.

Confirm. The caller resubmits the same parameters plus the step-up token and OTP. The service recomputes the action fingerprint and verifies the token against the subject, device fingerprint, and action fingerprint; any mismatch (including changed parameters or a different device) returns HTTP 401 with code error.msg.consumer.beneficiaries.command.stepup.invalid. It then validates the OTP, re-runs the name, account, and self-account checks, and persists. A duplicate name detected at either the application check or the database unique index returns HTTP 409.

Update follows the same initiate/confirm pattern but only the name and transfer limit are editable; the destination account fields are immutable (updatable = false on the entity). Delete is a single call with no challenge; it deactivates the row, which also frees the name for reuse (the unique index only covers active rows).

ABAC

ABAC (attribute-based access control: authorization decided from attributes of the caller and the request, not just a role name) is enforced in the service layer before any other work. The four actions BENEFICIARY_LIST, BENEFICIARY_ADD, BENEFICIARY_MODIFY, and BENEFICIARY_DELETE are defined in infrastructure.access.data.ActionPolicies as unowned policies requiring scope consumer:full and a kyc_verified: true JWT claim. Open banking consent tokens therefore cannot reach any beneficiary endpoint. Denials publish an ACCESS_DENIED audit event.

The policies carry no resource-ownership rule because ownership is structural: every repository query is keyed by the user id resolved from the JWT subject (findByPublicIdAndUserIdAndActiveTrue, findAllByUserIdAndActiveTrueOrderByNameAsc). A caller who guesses another user’s beneficiary public id gets HTTP 404, not someone else’s data.

Storage and Fineract interaction

Beneficiary data lives entirely in the BFF’s PostgreSQL database. Fineract holds no beneficiary record and is never written to by this module. Fineract is called only during add-time validation, and all three calls are reads: savings search, savings account retrieval, and client retrieval. The resolved Fineract office, client, and account ids are stored on the BFF row so later transfers need no re-resolution.

Interaction with transfers

A transfer does not reference a beneficiary by public id. The caller submits a destination account id and type, and transfers.command.service.TransfersCommandServiceImpl.requireDestinationAllowed decides:

  1. A loan destination never consults beneficiaries: the caller must own the loan (ABAC ownership check), otherwise the transfer is rejected with TransferAccessDeniedException.

  2. For a savings destination the service first calls BeneficiariesQueryService.findActiveByAccount(userId, toAccountId), which matches active savings-type beneficiary rows only. If the matched beneficiary has a transfer limit, an amount above it is rejected with TransferBeneficiaryLimitExceededException; a null limit means unlimited.

  3. With no beneficiary match, the caller must own the destination savings account (ABAC ownership check), otherwise the transfer is rejected with TransferAccessDeniedException.

findActiveByAccount is an internal method on the query service, not an HTTP endpoint, and performs no ABAC authorize of its own; the transfers service has already authorized TRANSFER_EXECUTE. Because the check is by account id, deleting a beneficiary immediately closes the transfer path to that account.

Design rationale

  • Two-phase initiate/confirm with an OTP plus a step-up token binds the challenge to the subject, the device fingerprint, and a hash of the exact request parameters, so an attacker with a stolen session cannot replay the challenge from another device or swap in a different destination account between initiate and confirm.

  • Beneficiaries are BFF state rather than Fineract state because Fineract has no consumer beneficiary concept; keeping the allow-list in the BFF makes the BFF the policy enforcement point for outbound transfers, consistent with its role.

  • Storing resolved Fineract ids at add time means the hot transfer path costs one indexed local lookup instead of upstream search calls.

  • The office-name knowledge check raises the bar for registering an arbitrary account number, and account status filtering prevents registering closed accounts.

  • Registering one of the caller’s own accounts is rejected so that transfers to own accounts always flow through the ABAC ownership path, keeping a single authority for own-account access instead of a duplicate beneficiary row.

  • Soft delete preserves history for auditability while the partial unique index still allows the name to be reused.

  • Query responses expose the public id, name, limit, and the resolved Fineract savings account id. The account id is deliberately included so the transfer form can submit it as the transfer destination; office and client ids never reach the browser.

Limitations and future work

  • The list endpoint returns the raw Fineract account id. There is no masked account number or holder name, so the customer cannot verify from the list which real account a beneficiary points at beyond the caller-chosen label, and an internal Fineract identifier is exposed to the client.

  • OTP delivery is email only. No other channel is implemented for this flow.

Account Summary

The summary module (org.apache.fineract.consumer.summary) serves the dashboard view of the consumer application: one call that returns every savings and loan account belonging to the logged-in client, with balances. It is a query-only module. It has no command/ subtree, no database tables, and no Liquibase changesets; it holds no state of its own.

Endpoints

Method Path Purpose Auth requirements

GET

/api/v1/summary/accounts

Valid access JWT (a signed token proving who the caller is), delivered as an httpOnly cookie and resolved by the resource-server filter chain. How aggregation works

Despite covering two product types, the endpoint makes exactly one upstream call. Fineract Core already exposes a combined view, GET /v1/clients/{clientId}/accounts, which returns savings and loan accounts in a single response. The service calls it through the generated Feign client ClientApi.retrieveAllClientAccounts(clientId) (Feign: a library that turns an annotated Java interface into an HTTP client). There is no fan-out to the savings or loans modules and therefore no parallelism to manage.

The flow is:

  1. AccessPolicyEvaluator.authorize(jwt, SUMMARY_VIEW) enforces the ABAC policy.

  2. UserClientResolver.resolveClientId(jwt) maps the JWT subject (a public UUID) to the BFF user record and returns its bound Fineract client id. The caller can never supply a client id.

  3. One Feign call to GET /v1/clients/{clientId}/accounts.

  4. The response is mapped into BFF DTOs: SavingsSummaryItemQueryData (id, account number, product name, status, active flag, currency, account balance, available balance) and LoanSummaryItemQueryData (id, account number, product name, status, active flag, currency, loan balance, amount paid), wrapped in AccountsSummaryQueryData. For both product types the status field carries Fineract’s machine-readable status code, and active is derived from the same upstream status object. Both lists are sorted by id ascending, nulls last. Fineract response shapes are never returned to the client.

Because there is a single upstream call, there is no partial-failure mode. Any FeignException is translated to SummaryUpstreamUnavailableException, which maps to HTTP 502 Bad Gateway with the error code error.msg.consumer.summary.upstream.unavailable. The endpoint is all-or-nothing: it never returns a summary with one product type missing.

Caching

The aggregate is not cached. Every request goes to Fineract, so balances are always current. The shared OwnedAccountsCache in the infrastructure package caches the same upstream response for ABAC ownership checks (60 second in-process TTL, 300 second Valkey TTL), but the summary path does not read from it: SUMMARY_VIEW carries no ownership rule, and the service fetches fresh data for the response body.

ABAC

ABAC (attribute-based access control: authorization decided from attributes of the caller and the request, not just a role name) is enforced in the service before the upstream call. The SUMMARY_VIEW policy in infrastructure.access.data.ActionPolicies requires:

  • scope consumer:full, so an open banking consent token cannot call this endpoint;

  • a kyc_verified claim of true in the JWT;

  • no resource-ownership check, because the response is derived from the client id bound to the JWT subject rather than from a caller-supplied id. Scoping to the authenticated client is structural.

Denials publish an ACCESS_DENIED audit event with the action, reason, and user public id.

  • Unit: SummaryQueryServiceImplTest covers field mapping for savings and loans, id sorting, the empty-accounts case, translation of upstream Feign failures to SummaryUpstreamUnavailableException, and propagation of ABAC denials.

  • End to end: src/test/resources/features/summary.feature (glue in cucumber.steps.SummarySteps) runs a happy path against seeded savings and loan accounts and asserts that an unauthenticated request is rejected.

  • Frontend: a Playwright spec (frontend/playwright/tests/summary.spec.ts) covers the route guard: an unauthenticated visit to the dashboard redirects to login.

Design rationale

  • Delegating aggregation to Fineract’s own /clients/{clientId}/accounts endpoint keeps the module to one upstream call, avoiding the latency, ordering, and partial-failure complexity of fanning out to separate savings and loans endpoints.

  • Resolving the client id from the JWT subject, with no id parameter in the API, makes cross-client data access impossible by construction rather than by validation.

  • Query-only CQRS layout: the dashboard never writes, so the module carries no command side, entities, or repositories.

  • Deterministic sorting by id gives the frontend a stable render order without client-side logic.

Limitations and future work

  • No caching or degradation. Every dashboard load is a synchronous Fineract call, and any upstream error fails the whole response with a 502. A stale-if-error fallback or short-TTL cache could be added if dashboard load becomes a hot path.

  • The summary is limited to per-account rows. There are no cross-account totals, share accounts, or currency grouping. Callers that need totals must compute them.

User Profile

The user module owns the logged-in customer’s view of their own profile and the lifecycle of their BFF credentials (BFF: backend-for-frontend, the Spring Boot service that sits between the Angular client and Fineract Core). A "user" here is the BFF’s own account record: an email, a password hash, and a binding to exactly one Fineract client. The module serves four read endpoints (profile, charges, obligees, profile image) and four write endpoints, all of which concern the password (authenticated change, and the public forgot/reset pair).

There are no endpoints for updating profile fields. Name, email, mobile number, and the profile picture are maintained on the Fineract client record by back-office staff; the BFF only reads them.

Beyond its HTTP endpoints, the module exposes service methods that other modules call through the Spring Modulith named interfaces:

Profile picture handling

The read path is a proxy. UserQueryServiceImpl.getImage resolves the caller’s Fineract client id and calls Fineract GET /v1/clients/{clientId}/images through the generated client (DefaultApi.retrieveImage) with entity type clients and an Accept: text/plain header. Under that accept header, upstream Fineract (ImagesApiResource) base64-encodes the stored image and wraps it as a data URL; when both maxWidth and maxHeight are supplied it resizes first. The BFF returns the string unchanged inside UserImageQueryData.imageDataUri. A Fineract 404 is translated to the BFF’s own 404; any other Feign failure becomes a 502.

Writes are deliberately excluded. Fineract exposes create and delete operations on the same image resource, but the BFF offers no upload, replace, or delete endpoint. The photo is captured by back-office staff and serves as an identity-verification anchor: staff compare the person in front of them (or on a document) against the stored image. Letting the consumer overwrite it from a self-service channel would let a compromised session replace the very artifact used to detect that compromise. The profile response carries hasImage (from Fineract’s imagePresent flag) so the client can decide whether to fetch the image at all. This is a deliberate deviation from the deprecated self-service API, which allowed image upload.

The BFF stores no copy of profile data. Every profile, charges, obligees, and image read fetches live from Fineract via the generated Feign client (ClientApi, ClientChargesApi, DefaultApi); nothing from those responses is persisted locally.

Security

  • Contact details are masked before they leave the BFF. EmailMaskingService masks the email; the mobile number is reduced to ***-***- plus the last four digits. The raw email and mobile number are never returned by any endpoint in this module.

  • The password hash never crosses the HTTP boundary. It travels internally in UserCredentialsQueryData, whose toString is explicit-include-only so it cannot leak into logs; the same applies to every request DTO that carries a password or OTP.

  • Password change is a step-up flow with three factors: knowledge of the current password, possession of the email inbox (OTP), and a step-up token cryptographically bound to the caller’s public id, device fingerprint, and the action fingerprint of /api/v1/user/password/change. A step-up token minted for one device or one action cannot confirm another.

  • Both password-setting flows revoke all sessions, so a session an attacker holds dies the moment the legitimate user changes the password.

  • The forgot and reset endpoints are shaped against user enumeration: uniform 202 on forgot, one generic error code on reset, and log lines that record the failure without the submitted email.

  • KYC gating is differential: USER_CHARGES_LIST and USER_OBLIGEES_VIEW require the kyc_verified claim, while USER_PROFILE_VIEW, USER_IMAGE_VIEW, and USER_PASSWORD_CHANGE do not, so a customer whose Fineract client is not in good standing can still see who they are and recover their credentials, but cannot read financial data.

Design rationale

  • No local mirror of profile data. Fineract is the single source of truth for client details; the BFF proxies reads per request instead of synchronizing a copy, which removes an entire class of staleness and reconciliation problems at the cost of one upstream call per read.

  • Profile picture is read-only by design. The image anchors back-office identity verification, so the consumer channel must not be able to replace it (see Profile picture handling above).

  • Contact details are masked because the profile page has no need for the full values, and returning them would turn any XSS or logging slip into a PII leak.

  • The credential row lives in this module while session state lives in the authentication module. Password confirmation crosses that boundary through the AuthenticationCommandService interface rather than touching token storage directly, keeping each module’s persistence private.

  • Public forgot/reset endpoints return uniform responses so the login identifier space cannot be enumerated, matching the behavior of the login endpoint itself.

  • The differential KYC gate treats identity ("who am I, can I fix my password") as available to any bound user, and financial detail as gated, mirroring the ABAC policy split used across the read modules.

Limitations and future work

  • The fingerprint header is unused on reset paths. The X-Device-Fingerprint header is required on the public forgot and reset endpoints but is not bound into the reset flow or its audit events (they record a null fingerprint), so it adds no security value on those two paths.

  • Charges pagination lacks page metadata. The response returns totalFilteredRecords but not current page or total pages; clients must derive it.

Audit

The BFF (backend-for-frontend, the Spring Boot service in consumer/ that sits between the Angular client and Fineract Core) records security-relevant and user-activity events in a dedicated PostgreSQL table, separate from application logs. Auditing spans two code areas that must not be confused:

  • consumer.audit (feature module): the command side is the HTTP surface that ingests batched audit events posted by the Angular client, plus the persistence and retention machinery for the shared audit_events table. The query side is a demo-only, flag-gated read endpoint over the same table (see "Query surface" below).

  • consumer.infrastructure.audit (infrastructure package): the in-process contract that server-side features use to emit their own audit events. It defines the event type catalog, the severity model, and two listener annotations. It contains no persistence code of its own.

The two halves meet in the feature module: ServerAuditEventListener (in consumer.audit.command.service) subscribes to the infrastructure events and writes them into the same audit_events table that client submissions land in. Rows are distinguished by a source column: CLIENT for events reported by the browser, SERVER for events observed by the BFF itself. Server rows are trusted; client rows are best-effort telemetry and are validated accordingly.

Responsibility is split with Fineract Core. Fineract, as the system of record, audits backend financial operations and keeps the authoritative record of every posted transaction. The BFF audits the consumer channel instead, covering security events observed at the gateway (logins, denials, OTP challenges, consent grants) and telemetry reported by the browser. Successful financial operations are therefore not duplicated into audit_events; a completed transfer, for example, is recorded by Fineract and re-read from there on demand.

Authorization

The endpoint is covered by the deny-by-default rule in SecurityConfig (anyRequest().authenticated()), so an unauthenticated call is rejected before reaching the controller. DeviceFingerprintFilter additionally requires the X-Device-Fingerprint header to match the device_fingerprint claim in the JWT; a mismatch is rejected with 403 and itself emits a DEVICE_FINGERPRINT_MISMATCH server audit event. Inside the service, AccessPolicyEvaluator.authorize(jwt, ConsumerAction.AUDIT_EVENT_SUBMIT) applies the ABAC policy (attribute-based access control, authorization decided from attributes rather than fixed roles): the token must carry the consumer:full scope. KYC verification is deliberately not required, so pre-KYC users still produce audit trails. Open banking tokens cannot submit audit events.

Batching and limits

Batching happens on the client. frontend/src/app/core/audit/audit.service.ts buffers events in memory (buffer cap 50, oldest dropped first) and flushes up to 50 events per POST when any of the following occurs: the buffer reaches 20 events, a 30 second interval timer fires, the page becomes hidden, or a LOGOUT event is recorded. Failed flushes are requeued; after 3 consecutive failures the buffer is discarded so audit delivery can never wedge the app.

The server enforces its own limits from application.properties:

  • consumer.audit.max-batch-size=50: a larger batch is rejected wholesale with HTTP 413 (AuditBatchTooLargeException, code error.msg.consumer.audit.batch.too.large).

  • consumer.audit.max-details-bytes=2048: an event whose serialized details JSON exceeds this is dropped (counted as rejected), the rest of the batch proceeds.

Per-event validation

Each event in a batch is validated independently; a bad event is silently counted in rejected while the rest are stored. An event is rejected when:

  • eventUuid is not a parseable UUID.

  • eventType is not a known AuditEventType, or is a server-only type. The enum carries a clientSubmittable flag; only the six client types listed below are accepted, so a browser can never forge a LOGIN_SUCCESS or consent row.

  • the serialized details exceed max-details-bytes or fail the PII screen.

Replay is idempotent: event_uuid is unique in the database, and a duplicate-key violation on that constraint is treated as already stored and counted as accepted (AuditCommandServiceImpl.saveDeduplicating).

Timestamps: client claims are never authoritative

AuditEvent.forClientEvent stores the client-reported timestamp in the column occurred_at_claimed and always sets received_at to Instant.now() on the server. All server-side logic (retention purge, indexes, ordering) keys on received_at. The claimed time is retained only as forensic context and its column name marks it as untrusted.

PII screening

PII (personally identifiable information, data that identifies a person, such as an email address or a government ID number) must never enter the audit table. Two layers exist, both verified in code:

  • Client side, frontend/src/app/core/audit/pii-scrub.ts: scrubPii replaces email-, SSN-, Aadhaar-, and card-number-like patterns with [REDACTED]. buildDetails applies it to every value, drops blocked keys (password, otp, ssn, token, case-insensitive), and truncates each value to 300 characters before events are buffered.

  • Server side, AuditPiiScreen: the BFF does not trust the client scrub. It re-checks the serialized details JSON against regular expressions for email addresses, 9-digit runs (SSN-like), 12-digit runs (Aadhaar-like), 13 to 19 digit runs (card-like), and forbidden JSON keys (password, otp, ssn, token, case-insensitive). Any match drops that event (counted as rejected).

Server-emitted events bypass AuditPiiScreen; their details maps are composed by BFF code and are trusted not to contain secrets.

Server-side audit sink (infrastructure.audit)

consumer.infrastructure.audit is the emit-side contract. It holds four things: the AuditEventType catalog, the AuditSeverity enum, two immutable event payload classes (TransactionalAuditEvent, NonTransactionalAuditEvent), and two listener annotations. Features never write to the audit table directly; they publish a Spring application event and the audit feature module persists it. This keeps the dependency direction clean: every feature may depend on infrastructure, and only the audit module knows about storage.

Emitting an event

A feature injects Spring’s ApplicationEventPublisher and publishes one of the two payloads, for example (from AuthenticationCommandServiceImpl):

eventPublisher.publishEvent(TransactionalAuditEvent.of(AuditEventType.LOGIN_SUCCESS,
        user.getId(), false, command.getDeviceFingerprint(), null));

Both payload types carry a generated eventUuid, the AuditEventType, an optional userId, an unknownPrincipal flag (set when the actor could not be resolved, for example a login failure for a nonexistent username), an optional device fingerprint, and a small details map. Severity is not passed by the caller; it is fixed per event type on the enum.

The choice between the two payloads is about transactions:

  • TransactionalAuditEvent, consumed by methods annotated @TransactionalAuditListener (a meta-annotation for Spring Modulith’s @ApplicationModuleListener). Spring Modulith is a library that enforces module boundaries and provides a persistent event bus: the event is written to the event_publication table inside the publisher’s database transaction and delivered asynchronously after commit. Use this when the audit row must not appear if the business transaction rolls back, and must not be lost if the process crashes after commit. Used for LOGIN_SUCCESS, PASSWORD_CHANGE_CONFIRMED, CONSENT_CREATED, CONSENT_REVOKED.

  • NonTransactionalAuditEvent, consumed by methods annotated @NonTransactionalAuditListener (a meta-annotation combining @Async and @EventListener, enabled by AsyncConfig). Delivered immediately on a background thread with no transaction coupling. Used for failure paths and events that have no surrounding business transaction: login failures, OTP outcomes, refresh rejections, access denials, fingerprint mismatches, consent decisions (CONSENT_GRANTED / CONSENT_DENIED), and password-change initiation.

ServerAuditEventListener implements one listener method per annotation, maps the payload to an AuditEvent row with source=SERVER and received_at=now, and saves it. A duplicate eventUuid (possible because Modulith may redeliver an incomplete publication) is ignored. Any other persistence failure is logged and swallowed: an audit write must never fail the business operation it describes.

Separation from application logs

Audit events are rows in audit_events, not log lines. Application logs (SLF4J) are used around the audit path only for operational failures, for example a row that could not be persisted or a purge run summary, and never contain OTP values or ID numbers. The audit trail therefore survives log rotation, is queryable with SQL, and has its own retention policy.

Design rationale

  • One table, two sources. Client telemetry and server security events share audit_events so retention, indexing, and querying are implemented once, while the source column and the clientSubmittable flag keep the trust boundary explicit: the browser can only ever create rows of the six client types.

  • Event-driven emit path. Features publish Spring events instead of calling an audit service directly, so audit persistence cannot fail or slow a business operation, and the audit module remains the only code that knows about the table. The transactional/non-transactional split exists because some events must be atomic with a business transaction (a login success row without a session would be a lie) while failure events have no transaction to join.

  • Server-received time as the only trusted clock. Client clocks are routinely wrong or hostile; keeping the claim in a separately named column preserves forensic value without letting it influence server behavior.

  • Defense in depth on PII. Client scrubbing improves data quality; server screening is the actual control. Rejecting rather than scrubbing on the server keeps the BFF out of the business of rewriting evidence.

  • Severity fixed on the enum. Callers cannot inflate or downplay an event’s severity, and the catalog stays reviewable in one file.

Limitations and future work

  • There is no KYC-related event type. KYC submission is a security-relevant action, but AuditEventType contains no KYC_* entry and the identity module publishes no audit events.

  • Rejected client events are dropped silently. The drop happens per event; the {accepted, rejected} counts say how many were rejected but not which or why, which complicates client-side debugging.

  • The client buffer is in memory only. Events recorded just before a crash or hard tab close (outside the visibilitychange flush) are lost. That is acceptable for telemetry but worth noting for anyone tempted to treat CLIENT rows as complete.

  • Server-emitted details maps bypass the PII screen. They rely on the trust assumption that BFF code composes them safely.

Open Banking

The open banking module provides a demo of third-party access to a customer’s accounts with the customer’s explicit consent. A TPP (third-party provider: an external application acting on the customer’s behalf, for example an account-aggregation app) obtains a consent-scoped access token from the BFF and uses it to read the customer’s account list and balances. The surface is read-only. No TPP can move money or mutate anything through this module.

Code lives in two places:

  • consumer/src/main/java/org/apache/fineract/consumer/openbanking/ holds the feature module in the project CQRS layout (CQRS: commands and queries are separated end to end): the consent aggregate, its command and query controllers, services, repositories, and per-side entities.

  • consumer/src/main/java/org/apache/fineract/consumer/infrastructure/oauth2/ holds the OAuth2 plumbing: token customization, consent-ceremony validators, the refresh-grant consent check, the filter that authenticates the customer during the ceremony, and the database-backed TPP registry (the RegisteredTpp entity, its repository, and the RegisteredTppClientAdapter). The authorization server itself is Spring Authorization Server, configured in infrastructure/configs/OAuth2AuthorizationServerConfig.java and running in-process inside the BFF. The two sides are decoupled through two ports defined in the infrastructure package, OAuth2ConsentLookupPort and OAuth2ConsentRecorderPort, implemented by adapters in the feature module.

Consent model

A consent (a customer’s recorded permission for one TPP to read specific categories of their data, for a limited time) is a row in the BFF’s own database. It records:

  • the TPP client id that requested it,

  • the customer (BFF user public UUID), set at the moment the customer approves or denies,

  • the granted permissions (data categories),

  • creation time, expiry time, and the time of the last status change.

The OAuth2 flow

The flow is OAuth2 authorization code with PKCE (PKCE: a one-time code challenge that stops an intercepted authorization code from being replayed). PKCE is mandatory for every registered TPP (requireProofKey(true)).

TPP registration

Registered TPPs are rows in the BFF’s own registered_tpps table (changeset db/changelog/infrastructure/008-create-registered-tpps.yaml). Each row holds the client id, the client name, one redirect URI, a comma-delimited scope list (scope: a named permission carried inside the access token), a status (Postgres enum registered_tpp_status: ACTIVE or REVOKED), and onboarding/status timestamps. RegisteredTppClientAdapter implements Spring Authorization Server’s RegisteredClientRepository over that table. Every lookup reads the row live and filters on status, so only ACTIVE TPPs resolve; a REVOKED or unknown client id fails client authentication. Each row maps to a client that authenticates with HTTP Basic (client_secret_basic), is granted three grant types (client_credentials, authorization_code, refresh_token), and requires PKCE.

Client secrets are hashed at rest. The client_secret_hash column stores a Spring Security password-encoder string (encoder id prefix plus hash; the seeded rows use {bcrypt}), verified through the delegating PasswordEncoder at client authentication. The plaintext secret is never stored or served by the BFF.

There is no onboarding API: the adapter’s save() throws UnsupportedOperationException, and rows are inserted out-of-band with SQL. In production, a TPP must be verified and onboarded by an external open banking service before its row is inserted. consumer/scripts/seed-demo.sh registers two dev fixtures, both scoped to openbanking:consents,openbanking:accounts.read and both carrying the dev secret demo-tpp-secret:

Step by step
Figure 3. Consent ceremony: authorization code with PKCE, end to end

  1. The TPP creates a consent. It obtains a client_credentials token (scope openbanking:consents) from POST /api/v1/oauth2/token, then calls POST /api/v1/openbanking/account-access-consents with the requested permissions. The consent is stored as AWAITING_AUTHORISATION and its UUID is returned.

  2. The TPP redirects the customer to the authorize endpoint. The URL is GET /api/v1/oauth2/authorize with the standard parameters (client_id, redirect_uri, scope, code_challenge, code_challenge_method) plus a custom consent_id parameter. OAuth2ConsentAuthorizeRequestValidator rejects the request with invalid_request unless the consent exists, belongs to the requesting TPP, is still AWAITING_AUTHORISATION, and is unexpired. A consent can therefore be put through the ceremony exactly once.

  3. The customer logs in with the ordinary consumer login. There is no separate open banking credential store. If the browser has no consumer session, the authorize endpoint redirects to the Angular login page ({frontend}/login?returnUrl=…​). The customer authenticates through the normal pipeline: password, OTP second factor, device-fingerprint-bound session, access_token httpOnly cookie. OAuth2UserAuthenticationFilter then authenticates the authorize request by decoding that same cookie.

  4. The customer approves or denies on the consent page. The consent page is the Angular route /consent. The decision posts back to the authorization endpoint with a CSRF token (XSRF-TOKEN cookie, CookieCsrfTokenRepository). OAuth2ConsentDecisionCustomizer records the outcome through OAuth2ConsentRecorderPort: approval transitions the consent to AUTHORISED and binds the customer’s user id to it; denial transitions it to REJECTED. Approval and denial are audited (CONSENT_GRANTED / CONSENT_DENIED). Consent decisions are never persisted by Spring’s own consent service: PerCeremonyAuthorizationConsentService is a deliberate no-op, so the BFF’s consent row is the single source of truth and every ceremony re-collects the decision.

  5. The TPP exchanges the code. POST /api/v1/oauth2/token with the authorization code, the PKCE code_verifier, and Basic client authentication. A wrong verifier is rejected with invalid_grant.

  6. The access token is consent-scoped, narrower, and shorter-lived. OAuth2AccessTokenCustomizer stamps every open banking access token with purpose=openbanking, the tenant, the space-joined scopes, the consent_id, and kyc_verified. It is signed with ES256 using the same signing key as consumer login JWTs (key id from consumer.oauth2.kid, default bff-es256, published at /api/v1/oauth2/jwks). Its TTL is consumer.oauth2.access-token-ttl, default 5 minutes, versus 15 minutes for a consumer login token.

  7. Refresh is supported and rotating. Refresh tokens (consumer.oauth2.refresh-token-ttl, default 90 days) are single-use: reuseRefreshTokens(false) means every refresh mints a new refresh token and replaying the old one fails with invalid_grant. OAuth2RefreshTokenConsentValidator wraps the refresh grant and re-checks that the bound consent is still AUTHORISED and unexpired, so revoking the consent kills refresh immediately.

KYC live check at every mint

The project rule that kyc_verified is never carried forward between tokens applies here too. On both the authorization_code and refresh_token grants, OAuth2AccessTokenCustomizer calls ClientStandingChecker (in infrastructure/kyc/) to live-check that the customer’s bound Fineract client is still active, uncached and fail-closed. If not, the mint aborts with invalid_grant ("identity verification no longer valid"). The same checker guards consumer login and refresh.

Token separation

Consumer tokens and open banking tokens are mutually unusable, enforced by the purpose claim and two separate decoders. The consumer resource chain rejects any token that carries a purpose claim; the open banking resource chain (openbankingTokenJwtDecoder) requires purpose=openbanking. A consumer session cookie on an open banking endpoint, or an open banking bearer token on a consumer endpoint, both fail as unauthenticated. Both cases are covered by Cucumber scenarios.

List the caller’s own consents, newest first (TPP id, permissions, status, created, expires). Action OPENBANKING_CONSENT_VIEW, KYC required.

POST

/api/v1/openbanking/consents/{consentId}/revoke

Revoke an AUTHORISED consent the caller owns. Action OPENBANKING_CONSENT_REVOKE, KYC required. Audited as CONSENT_REVOKED.

ABAC scoping

The module is a policy enforcement point in two layers.

Scope layer. Every service method passes through AccessPolicyEvaluator with an action from the ABAC policy table (ActionPolicies). Each TPP read first authorizes OPENBANKING_ACCOUNTS_VIEW, which accepts only openbanking:accounts.read, then delegates to the consumer read services. Open banking tokens never carry consumer:full, so the only consumer actions they can reach are the ones whose policy explicitly lists openbanking:accounts.read: SAVINGS_LIST, LOANS_LIST, SAVINGS_VIEW, and LOANS_VIEW. Every other consumer action (transfers, beneficiaries, profile, loan applications) is consumer:full only, so a stolen open banking token cannot reach them. The TPP consent actions (OPENBANKING_TPP_CONSENT_CREATE, OPENBANKING_TPP_CONSENT_VIEW) accept only openbanking:consents and do not require kyc_verified, because a client-credentials token has no customer behind it yet.

Consent layer. On every TPP read, OpenBankingQueryServiceImpl.requireValidConsent re-loads the consent row named by the token’s consent_id claim and requires, atomically: status AUTHORISED, unexpired, the consent’s TPP matches the token audience, the consent’s user matches the token subject, and the requested permission is in the consent’s permission set. Any failure is a 403 (OpenBankingConsentInvalidException). Because this check reads the database on every request, revocation takes effect immediately even while an access token is still within its 5-minute TTL.

Account restriction falls out of reuse: the open banking token’s subject is the consenting customer’s user id, and the reads delegate to the same SavingsQueryService and LoansQueryService the consumer app uses, which resolve accounts from the caller’s bound Fineract client. A TPP can only ever see the accounts of the customer who approved the consent.

Auditing

The flow emits structured server-side audit events: CONSENT_CREATED (TPP creates), CONSENT_GRANTED / CONSENT_DENIED (customer decides), CONSENT_REVOKED (customer revokes), and ACCESS_DENIED from the policy evaluator on any scope, KYC, or ownership failure. Events carry the consent id, TPP client id, and the customer’s public id, never account data.

Design rationale

  • One auth stack, not two. The module deliberately reuses the consumer login pipeline instead of forking it: the customer authenticates the authorize ceremony with the same device-fingerprint-bound session cookie minted at login, open banking tokens are signed with the same ES256 key as consumer JWTs, and the same ClientStandingChecker fail-closed KYC check guards every mint on both pipelines. The differences are data, not code paths: a purpose claim, a narrower scope set, and a shorter TTL.

  • The consent row is the single source of truth. Spring’s own consent persistence is disabled, so consent state lives in exactly one place, open_banking_consents, and every enforcement point (authorize validation, refresh validation, per-read check) reads it live. That is why revocation is immediate rather than eventual.

  • Defense in depth over trust in the token. A valid open banking access token is necessary but not sufficient: every read re-verifies the consent’s status, expiry, TPP binding, user binding, and permission against the database. Token theft within the 5-minute window yields nothing once the consent is revoked.

  • Ports between infrastructure and feature. The OAuth2 plumbing depends on OAuth2ConsentLookupPort and OAuth2ConsentRecorderPort, not on the feature module, keeping the authorization server generic and the consent domain logic inside the bounded context.

  • Open Banking UK-flavored contract. Resource naming (account-access-consents), permission names (ReadAccountsBasic, ReadBalances), status names (AWAITING_AUTHORISATION), and balance types (ClosingBooked, InterimAvailable) follow the Open Banking UK read API vocabulary so a later evolution toward that specification changes payload detail, not the model.

Limitations and future work

  • Local demo only, not FAPI-certified. FAPI (Financial-grade API: the hardened OAuth2 profile real open banking regimes require) expects mTLS or private_key_jwt client authentication, pushed authorization requests, and sender-constrained tokens. The dev and demo stack uses client_secret_basic; a production deployment puts mTLS (mutual TLS: both sides present and verify certificates) between open banking providers and the open banking endpoints. The PAR endpoint path exists in the server settings but is not required or exercised.

  • Consent is data-category-granular, not account-granular. An AUTHORISED consent with ReadAccountsBasic exposes all of the customer’s accounts. There is no per-account selection at the consent page.

  • Read surface is accounts and balances only. No transactions, direct debits, standing orders, or parties endpoints exist on the TPP surface, and no payment-initiation surface at all.

  • No expiry housekeeping. Expired consents are correctly rejected at every use, but rows stay in AWAITING_AUTHORISATION or AUTHORISED forever; there is no scheduled transition to an expired status or retention sweep.

  • consent_id rides as a custom authorize parameter. It does not ride inside a signed request object as Open Banking UK’s intent id does, so the parameter is integrity-protected only by the server-side validation, not by a client signature.

  • Long-lived refresh tokens. The 90-day default refresh and consent TTLs are demo conveniences; a production deployment would want re-authentication ceilings aligned with regulatory 90-day re-confirmation rules rather than a silent 90-day refresh chain.
