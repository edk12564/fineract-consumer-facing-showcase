Development

This chapter covers the day-to-day developer workflow. It explains how to build the backend and frontend, run unit and end-to-end tests, regenerate the API clients, and run the demo stack locally.

Build and Test

This section describes the developer workflow for the consumer-facing BFF (backend-for-frontend, the Spring Boot service in consumer/ that sits between the Angular client and Fineract Core) and the Angular demo client in frontend/.

Prerequisites

  • JDK 21. The Gradle build declares a Java toolchain of 21 in consumer/build.gradle, and CI builds with JDK 21. Gradle itself is provided by the checked-in wrapper (./gradlew, Gradle 8.14.4), so no separate Gradle install is needed.

  • Docker with Compose v2. Every backend test run starts the full stack (BFF, Fineract, two PostgreSQL databases, Valkey, Mailpit) with docker compose.

  • Node 22 and npm 10 or newer for the frontend. frontend/package.json pins "node": ">=22.0.0 <23.0.0", and frontend/.nvmrc contains 22.

  • openssl, used once to generate the development JWT signing key.

Before the first backend stack start, generate the development JWT signing key (a JSON Web Token is the signed access token the BFF issues to clients; the stack mounts this key into the BFF container):

cd consumer
./scripts/generate-dev-jwt-key.sh

The script is idempotent: it writes consumer/dev-jwt-key.pem and leaves an existing key untouched.

The local Docker stack

The stack is defined in consumer/compose.yaml and is the only local test environment: there is no embedded database or mocked Fineract. It runs:

  • bff on host port 8080, the system under test

  • fineract (Apache Fineract 1.12.1) on host port 8888

  • bff-db (PostgreSQL) on 5432 and fineract-db on 5433

  • valkey (a Redis-compatible key-value store) on 6379

  • mailpit (a development SMTP catcher; OTP emails land in a web inbox) on 8025

The compose stack exists for development and demo use. Real providers implement their own production stack: DDoS protection, per-IP rate limiting, and external key storage such as a KMS are deployment concerns that sit outside what the dev stack provides. The same applies to storage: the stack’s databases run on tmpfs (in-memory storage), which is useful for local development and tests, and real deployments use volumes instead.

Every backend command follows the same pattern: bring the stack up, run the Gradle task, tear the stack down with -v. The -v flag removes the volumes together with the containers, so the next run starts from a clean database instead of inheriting state from the previous one. The first up takes roughly two minutes because Fineract is slow to boot; later runs are faster.

Backend unit tests

Unit tests are JUnit 5 tests that mock at service and port interfaces. Run from consumer/:

cd consumer
docker compose up -d --build --wait && ./gradlew test; docker compose down -v

The test source set compiles against the generated Java API client (see the OpenAPI pipeline below), and generating that client requires the stack: the openapi task scrapes the spec from the running application. The test task itself does not regenerate the client. On a fresh checkout, run ./gradlew generateJavaClient once with the stack up; once consumer/build/generated/java-client exists, ./gradlew test runs with the stack down.

Backend end-to-end tests (Cucumber)

Cucumber is a behavior-driven test framework: plain-text .feature files describe scenarios, and Java "step glue" classes execute them as real HTTP requests against the BFF container at http://localhost:8080.

cd consumer
docker compose up -d --build --wait && ./gradlew cucumber; docker compose down -v

Feature files cover registration, login, savings, loans, transfers, beneficiaries, summary, profile, password, audit, open banking, rate limiting, and ABAC denial paths.

OpenAPI pipeline and generated clients

OpenAPI is a machine-readable description of an HTTP API. The BFF’s spec is not written by hand: springdoc generates it from the running application, and the openapi Gradle task scrapes it from http://localhost:8080/v3/api-docs into consumer/build/openapi/openapi.json. The stack must therefore be up for any task in this pipeline.

Two clients are generated from that spec:

  • generateJavaClient produces a Java Feign client (Feign is a declarative HTTP client library) in consumer/build/generated/java-client. The Cucumber test harness compiles against it.

  • generateTypescriptClient produces a TypeScript Angular client in frontend/src/openapi-client, imported by the frontend under the path alias @bff/client.

Always delete the old output directory first. The generator only adds and overwrites files; it does not remove files for endpoints that no longer exist, so stale services linger otherwise. Both directories are gitignored generated output, so nothing tracked by git is at risk. Run from consumer/:

cd consumer

# Java client (Cucumber test harness)
rm -rf build/generated/java-client
docker compose up -d --build --wait && ./gradlew generateJavaClient; docker compose down -v

# TypeScript client (Angular app)
rm -rf ../frontend/src/openapi-client
docker compose up -d --build --wait && ./gradlew generateTypescriptClient; docker compose down -v

# Both at once
rm -rf build/generated/java-client ../frontend/src/openapi-client
docker compose up -d --build --wait && ./gradlew openapi generateClients; docker compose down -v

A separate task, generateFineractClient, generates the BFF’s own Feign client to Fineract Core from a vendored Fineract spec. It runs automatically as part of compileJava and needs no running stack.

Frontend tests

Unit tests use Vitest (a fast test runner in the Vite ecosystem) through the Angular CLI. Specs are .spec.ts files colocated with the code under frontend/src/app/.

cd frontend
npm test

End-to-end tests use Playwright (a browser automation framework) against the full dockerized stack, defined in docker-compose.e2e.yml at the repository root. That compose file includes consumer/compose.yaml and adds the nginx-served Angular app on port 4443. One command brings the stack up, regenerates the TypeScript client, runs the specs, and tears everything down with -v:

cd frontend
npm run e2e:stack:run

Continuous integration

The GitHub workflows in .github/workflows/ run:

  • build-tests-backend.yml: on changes under consumer/, sets up JDK 21, generates the dev JWT key, starts the Docker stack, captures the OpenAPI spec and generates both clients (uploaded as artifacts), then runs ./gradlew test and ./gradlew cucumber, and tears down with docker compose down -v.

  • build-tests-frontend.yml: on changes under frontend/, consumer/, or the e2e compose file, runs two jobs. The unit job starts the backend, generates the TypeScript client, runs a production build (npm run build), and runs npm test — --no-watch. The e2e job brings up the full stack with npm run e2e:docker:up, runs npm run e2e (Playwright), and tears down with -v.

  • prettier-eslint.yaml: on changes under frontend/, runs npm run lint (ESLint) and npm run format:check (Prettier) against the frontend sources.

  • category-x-check.yml: two jobs. The backend job runs ./gradlew checkLicense to gate Gradle dependency licenses against the ASF allowlist and warns on Category B licenses. The frontend job generates an npm license report with license-checker-rseidelsohn and checks it against frontend/allowed-licenses.json with the same Category A pass, Category B warn, otherwise fail rules.

  • codeql.yml: CodeQL static analysis on push, pull request, and a weekly schedule.

  • apache-rat.yml: Apache RAT scan for missing license headers.

  • i18n-check.yml: runs npm run i18n:check to verify frontend translation keys.

  • pr-test-count.yml: counts tests at the base and head of a pull request and posts a comparison comment.

  • zizmor.yml and asf-allowlist-check.yml: security linting of the GitHub workflows themselves and ASF contributor allowlist checks.

Where tests live

  • Backend unit tests: consumer/src/test/java/org/apache/fineract/consumer/, mirroring the feature packages (savings/, loans/, transfers/, openbanking/, and so on).

  • Cucumber feature files: consumer/src/test/resources/features/.

  • Cucumber step glue: the org.apache.fineract.consumer.cucumber package (steps under cucumber.steps), configured as the glue path in consumer/build.gradle.

  • Frontend unit specs: *.spec.ts files next to their subjects under frontend/src/app/.

  • Playwright specs: frontend/playwright/tests/.

Design rationale

There is deliberately no test tier between unit and end-to-end: no Spring context slices, no Testcontainers, no mocked Fineract. Anything that needs real wiring runs against the same Docker stack that CI uses, which keeps local and CI behavior identical. Generating clients from the running app’s spec, rather than hand-writing them, makes the BFF contract the single source of truth for both test harness and frontend.

Limitations and future work

Full-stack runs are slow: the stack rebuilds and Fineract reboots on every cycle, so a single Cucumber run costs several minutes of setup. The client generation steps require manual rm -rf of previous output; the build does not clean stale files itself.

Running the Demo

This section describes how to run the full application locally. The running stack consists of the BFF (backend-for-frontend), Apache Fineract, and the Angular client served through nginx.

Start the stack

All commands run from frontend/. The stack is defined in docker-compose.e2e.yml at the repository root, which includes the backend stack from consumer/compose.yaml and adds the nginx-served Angular app.

cd frontend
npm run e2e:docker:up

This command generates the development JWT signing key if it does not exist, builds and starts the backend containers, regenerates the TypeScript API client from the running BFF, then builds and starts the frontend container. The first start takes roughly two minutes because Fineract is slow to boot.

Once up, the services are reachable at:

  • http://localhost:4443: the Angular app (nginx, container port 80 mapped to host 4443)

  • http://localhost:8080: the BFF API

  • http://localhost:8025: Mailpit, a development SMTP catcher. OTP emails (one-time passwords sent during registration and login) land here instead of a real inbox.

  • http://localhost:8888: Fineract Core (admin API, credentials mifos/password)

Seed demo data

The seeder stands in for the upstream back-office service: it creates verified client records in Fineract directly, then binds two of them to BFF users by driving the real registration endpoints, reading each OTP from Mailpit. It requires jq (a command-line JSON processor), the docker CLI (it inserts open banking TPP rows with docker exec into the bff-db container), and the stack to be up.

../consumer/scripts/seed-demo.sh

The script is idempotent: rerunning it skips clients that already exist.

What the seeder creates

In Fineract:

  • SSN and Aadhaar entries under the "Customer Identifier" code, a "Cash" payment type, a "Demo Savings" product (USD, 5% nominal annual interest), a "Demo Loan" product (USD, 12 monthly repayments, 2% interest per period), and three charge definitions: "Demo Client Fee" (25 USD), "Demo Savings Fee" (10 USD), and "Demo Loan Fee" (50 USD).

  • Four active clients: John Doe, Alan Turing, Grace Hopper, and Katherine Johnson (external IDs demo-client-1 through demo-client-4). Each client gets a government ID identifier (SSN or Aadhaar).

  • Clients #1 (John Doe) and #2 (Alan Turing) get a small data set: one active savings account with a 1,000 deposit and one disbursed 10,000 loan with a single 900 repayment. They carry no charges or guarantors by design.

  • Clients #3 (Grace Hopper) and #4 (Katherine Johnson) get a scaled data set each:

    • 10 savings accounts with opening deposits from 500 to 5,000, plus 10 further deposits and withdrawals spread over February to July 2024 and 10 savings-to-savings transfers between their own accounts (August to November 2024).

    • 10 loans: 7 active (disbursed), 2 pending approval, and 1 disbursed then repaid in full (closed). Each of the 7 active loans carries 25 repayments, 175 per client.

    • 3 client charges, 3 savings charges (on the first 3 savings accounts), and 3 loan charges (on the first 3 active loans).

    • Guarantors wired between the two: each guarantees the other’s first pending loan with a 100 amount funded from savings, and each has two further loans with a plain guarantor (the other client on one, an external person on the other: Marcus Aurelius and Ada Lovelace).

In the BFF:

  • Two rows in the registered_tpps table (a TPP, third-party provider, is an external application granted consent-scoped access): demo-tpp ("Demo TPP", redirect http://localhost:9999/tpp/callback, used by the Cucumber tests) and postman-tpp ("Postman TPP", redirect https://oauth.pstmn.io/v1/callback, used with Postman). Both are ACTIVE with scopes openbanking:consents and openbanking:accounts.read.

  • Clients #3 (Grace Hopper) and #4 (Katherine Johnson) are bound to BFF login accounts through the real registration flow, including OTP verification.

Demo credentials

The script prints a summary when it finishes: a per-client table (client IDs, savings and loan counts, login emails), a second table with charge, guarantor, and obligee counts for clients #3 and #4, and the two TPP registrations. The pre-bound logins are:

  • demo3@example.com (Grace Hopper) and demo4@example.com (Katherine Johnson), both with password DemoPassw0rd!23.

Clients #1 and #2 have no BFF user. Use them to demo the live registration flow; their identifier document keys are printed in the script source (consumer/scripts/seed-demo.sh) and the resulting OTP email appears in Mailpit.

Tear down

cd frontend
npm run e2e:docker:down

This runs docker compose down -v, which removes the containers and their volumes so the next start begins from a clean database.

Open banking demo tokens

consumer/scripts/seed-openbanking.sh mints third-party access tokens for Postman by driving the real OAuth2 authorization-code flow with PKCE (Proof Key for Code Exchange, a challenge that prevents a stolen authorization code from being redeemed by anyone else) headlessly: TPP client-credentials token, consent creation, customer login with the emailed 2FA code read from Mailpit, consent approval, and code exchange. A TPP (third-party provider) is the external application granted read-only, consent-scoped access.

It requires jq, the stack up, and seed-demo.sh already run, since it authenticates as a seeded TPP and as the seeded customer demo3@example.com. By default it uses the postman-tpp registration (redirect https://oauth.pstmn.io/v1/callback). Run from the repository root:

./consumer/scripts/seed-openbanking.sh

To drive the Cucumber TPP registration instead, override all three variables to match its seeded row:

TPP_CLIENT_ID=demo-tpp \
TPP_CLIENT_SECRET=demo-tpp-secret \
TPP_REDIRECT_URI=http://localhost:9999/tpp/callback \
./consumer/scripts/seed-openbanking.sh

On success it prints values ready to paste into a Postman environment: obClientId, obConsentId, obAccessToken, and obRefreshToken, plus the granted scope and the access-token lifetime. Unlike seed-demo.sh, this script is not idempotent: every run creates a new consent row and a new token pair, leaving the previous consent behind.

See Open banking for the consent model and endpoint surface.

Design rationale

The demo reuses the end-to-end test stack rather than a separate demo deployment, so what a demo audience sees is exactly what the tests exercise. The seeder binds users through the real registration endpoints instead of inserting rows directly, which keeps the seeded state indistinguishable from state produced by the application.

Limitations and future work

The stack is for development and demo use only. It runs cleartext HTTP on the Docker network, keeps a generated signing key on disk, and uses Mailpit in place of a real mail provider, so it should not be exposed beyond localhost. Real providers implement their own production stack (see the Build and Test section). Startup is slow because Fineract reboots from scratch each time.
